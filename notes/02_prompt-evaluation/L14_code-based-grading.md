## 1. このレッスンの目的
生成されたコードが「指定の形式で、その言語として正しく解析できるか」を、コードで機械的に採点する。さらに、L13 のモデルグレーダーの点と統合して、最終スコアにする。

## 2. コード採点の仕組み(ページ)
| 基準 | 担当 |
|---|---|
| 形式: 説明なしで、要求されたコードタイプ(Python・JSON・Regex)のみを返す | コードグレーダー |
| 有効な構文: その言語として正しく解析できる | コードグレーダー |
| タスクの遵守: 求められたことに直接対応し、正確である | モデルグレーダー |

## 3. 構文検証の3関数(ページ)
解析に成功すれば 10、失敗すれば 0 を返す。
| 形式 | 解析に使うもの | 失敗時の例外 |
|---|---|---|
| JSON | `json.loads(text.strip())` | `json.JSONDecodeError` |
| Python | `ast.parse(text.strip())` | `SyntaxError` |
| 正規表現 | `re.compile(text.strip())` | `re.error` |

```python
def validate_json(text):
    try:
        json.loads(text.strip())
        return 10
    except json.JSONDecodeError:
        return 0
```
(Python・正規表現も同じ形で、解析関数と例外が違う。)

## 4. データセットの変更(ページ)
どの検証関数を使うかを決めるため、各テストケースに期待する形式を持たせる。
```json
{ "task": "Create a Python function to validate an AWS IAM username", "format": "python" }
```
データセット生成プロンプトの出力例にも `format` を入れれば、自動で付く。

## 5. プロンプトの改善(ページ)
- 出力形式を具体的に指示する。
  - 「Respond only with Python, JSON, or a plain Regex」(Python・JSON・正規表現のみ返す)
  - 「Do not add any comments or commentary or explanation」(コメントや解説を加えない)
- ページはさらに、プリフィル(```` ```code ````)の併用も紹介している(現行環境では使わない。上の注意を参照)。

## 6. スコアの統合(ページ)
```python
model_grade = grade_by_model(test_case, output)
model_score = model_grade["score"]
syntax_score = grade_syntax(output, test_case)
score = (model_score + syntax_score) / 2
```
- 内容の品質と技術的な正しさに、等しい重みを与える。用途に応じて、重みは調整できる。

## 7. 実装のテスト(ページ)
評価を実行して、ベースラインのスコアを得る。スコア自体の良し悪しは問題ではない。重要なのは、プロンプトの改良で改善できるか。主観ではなく、数値でプロンプトエンジニアリングの進捗を測れる。

## 質疑(学習中の確認)
範囲: このレッスン(L14)の内容と、演習 ex10。

### 質問1: フェンス付きの Python を `validate_python` に渡すと何点か
出題: 出力が「```` ```python ````〜```` ``` ````」で囲まれた関数のとき、`validate_python` は何点か。
- YUTAの回答: A(10点。関数の中身は正しい Python なので)
- 評価: 不正解。正解は B(0点)。
  - B が正しい理由: `.strip()` が取るのは前後の空白と改行だけ。先頭の ```` ```python ```` は Python として不正で、`SyntaxError` となり、`except` で 0 が返る。形式違反(フェンス付き)が、構文エラーとして検出される。
  - A: 「中身が正しいから」は人間の見方。検証関数は、中身だけを切り出す処理を持たない。
  - C(5点): 関数が返すのは 0 か 10 だけ。中間値を返す処理はない。
  - D(エラーで止まる): `except SyntaxError` で受けているので、例外は処理され、0 が返る。
- 設計の選択(厳格 vs 寛容):
  | 方針 | 内容 | 捨てるもの |
  |---|---|---|
  | 厳格(ページの形) | フェンスがあれば 0 点 | 中身は正しい出力でも 0 点になる |
  | 寛容 | フェンスを取り除いてから検証する | 「説明なしの生のコードだけ」という要件が、評価で見えなくなる |
  L11 の要件が「クリーンな出力」なので、厳格な方が要件に合う。

### 質問2(振り返り1): ベースラインで構文が 0 になったのはどれか
- YUTAの回答: 「コードブロックの ``` が含まれていた」
- 評価: 正解。全3件(python・json・regex)が 0 だった。

### 質問3(振り返り2): 等しい重みで平均した結果、何が起きたか
- YUTAの回答: 「構文が 0 の為、モデルの 1/2 となっている」
- 評価: 半分正解。計算は合っている。足りないのは意味。等しい重みだと、構文が1回失敗しただけで、中身の評価(8〜9点)にかかわらず、最終点が約半分(4.0〜4.5)に下がる。
- 重みの設計(私の整理で、公式の指定ではない):
  - 構文が通らないと後段が動かない用途(出力をそのままプログラムに渡す等)なら、構文を重く見る(通らなければ 0 にする等)。
  - 人が読む用途で、記号を後で取り除けるなら、構文の重みを軽くする。

### 質問4(振り返り3): `re.compile` に普通の文章(`"hello"`)を渡すとどうなるか
- YUTAの回答: 「エラー」
- 評価: 誤り。`re.compile("hello")` はエラーにならない。普通の文字列は、そのまま「文字どおりに一致する正規表現」として有効。エラーになるのは、`"[a-z"` や `"("` のように、括弧が閉じていないものなど。
- 意味: regex の 10 点は、「構文が正しい」ことしか示さない。「EC2 のインスタンス ID に一致する」ことは示さない。中身の確認には、一致すべき文字列・一致すべきでない文字列を使ったテストが要る(私の補足)。

### 質問5(振り返り4): 今回の比較から分かったこと
- YUTAの回答: 「プロンプトにより得たい結果を明示する必要がある」
- 評価: 正解(やや曖昧)。言い換え: 出力形式をプロンプトで明示すると、構文の失敗を防げる。また、モデルの点は形式の不備を見逃したが、コードの構文チェックは見逃さなかったので、2つの採点を併用する意味がある。

- 途中のエラー: `json.load(text.strip())` と書いて、`AttributeError: 'str' object has no attribute 'read'`。
  - 読み解き: `json.load` は「ファイルオブジェクト」を受け取り、`.read()` を呼ぶ。文字列(str)には `read` がない。文字列を解析するのは `json.loads`(末尾の s は string)。
- 比較結果(同じ3件、各1回):
  | 項目 | ベースライン | TODO 5 の版 |
  |---|---|---|
  | 平均 | 4.17 | 9.17 |
  | 構文の点(python / json / regex) | 0 / 0 / 0 | 10 / 10 / 10 |
  | モデルの点(python / json / regex) | 8 / 8 / 9 | 8 / 9 / 8 |
- 読み取り:
  - 差の原因は構文の点。モデルの点はほぼ同じ(8〜9)。
  - ベースラインの出力は、構文が全件 0 なのに、モデルの点は 8〜9 だった。モデルは、フェンス付きの出力を「良い解答」と見た。モデルグレーダーだけでは、形式の不備に気づけなかった。コードグレーダーの意味はここにある。
  - TODO 5 の版でも、実行のたびに点はぶれた(平均 9.0 と 9.17。regex のモデルの点が 7 と 8)。ただし、構文の 0 と 10 の差は、そのぶれを大きく超える。
  - 3件・各1回の結果。件数を増やすと、変わる可能性がある。
- TODO 5 のプロンプトの文面: 追加した指示は「Python、JSON、または正規表現のみを返してください」「コメント、解説、説明、コードブロックの(```)を付けないでください」。プリフィルは使っていない。

## 【補足】ページ外の内容(私の整理)
- `re.compile` は寛容で、普通の文字列でも成功する(私の知識で、公式ドキュメントでの確認は、していない)。実機で、`hello` が通ることを確認していない場合は、ご自身で一度試すとよい。
- 「フェンス付きは 0 点」という厳格な設計と、「フェンスを取り除く」寛容な設計は、用途で選ぶ。後段の処理がフェンスを受け付けるかで決まる。
- 構文チェックの次の段階は、中身のチェック。たとえば、JSON ならキーの有無、Python なら関数の実行テスト、正規表現なら一致・不一致のテスト。これらは、期待結果をケースごとに用意する手間がかかる(L13 の質問2と同じ論点)。
- 試験ガイドとの関係: ガイドの全文を検索したが、このレッスンを直接扱う項目は、確認できなかった。評価パイプラインの考え方は、プロンプトの品質を測る話で、ガイドとの対応づけは、私の判断(公式の指定ではない)。
