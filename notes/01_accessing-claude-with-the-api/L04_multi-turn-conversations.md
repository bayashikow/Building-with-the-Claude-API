## 1. このレッスンの目的
Claude API は、会話の履歴を保存しない。マルチターン会話(複数回のやり取りで、文脈を保つ会話)を行うには、会話の状態を、自分のコード側で管理する必要がある。その方法を学ぶ。

## 2. ステートレスという性質
- Claude は会話履歴を一切保存しない。送るリクエストは、それぞれ完全に独立していて、以前のやり取りの記憶がない。
- 例: 「量子コンピューティングとは何ですか?」と聞いて、良い回答を得たあと、「もう一文書いてください」と続けても、Claude は何について言っているかわからない。量子コンピューティングの議論の記憶がないため、無関係な内容の一文を書いてしまう。

## 3. マルチターン会話の仕組み
文脈を保つために、2つのことを行う。
1. コード内で、すべてのメッセージのリストを、手動で維持する。
2. リクエストごとに、完全なメッセージ履歴を送る。

流れ(4ステップ)
1. 最初のユーザーメッセージを Claude に送る。
2. Claude の応答を受け取り、アシスタントメッセージとして、メッセージリストに追加する。
3. フォローアップの質問を、別のユーザーメッセージとして追加する。
4. 会話履歴全体を Claude に送る。

## 4. ヘルパー関数(3つ)
| 関数 | 役割 |
|---|---|
| `add_user_message(messages, text)` | `{"role": "user", "content": text}` を、リストに追加する |
| `add_assistant_message(messages, text)` | `{"role": "assistant", "content": text}` を、リストに追加する |
| `chat(messages)` | `client.messages.create()` に、履歴全体を渡して呼び出し、応答の本文を返す |

- ページの `chat()` は、`message.content[0].text` で本文を返す。モデルは、変数 `model`、`max_tokens=1000`。

## 5. 使い方の流れ(ページの例)
1. 空のリスト `messages = []` から始める。
2. `add_user_message` で、最初の質問を追加する(例: 量子コンピューティングを一文で定義する)。
3. `chat(messages)` で、応答を取得する。
4. `add_assistant_message` で、その応答を履歴に追加する。
5. `add_user_message` で、フォローアップ(「もう一文書いてください」)を追加する。
6. `chat(messages)` で、完全な文脈のもとで、フォローアップの応答を取得する。

結果: 完全な文脈を渡したので、Claude は、「もう一文書いてください」が、量子コンピューティングの定義を拡張するものだと理解する。

## 6. まとめ(ページの結び)
これらのヘルパー関数は、Claude を使った作業全体で役立ち、複数回のやり取りにわたって、意味のある会話を維持するアプリケーションを作りやすくする。

## 質疑(学習中の確認)
範囲: このレッスン(L04)の内容と、L03 の `content` の構造。

### 質問1: アシスタントの回答を履歴に足さずに、続けて送ると、どうなるか
- 設定: `add_assistant_message(messages, answer)` の行を消して、2つ目のユーザーメッセージ(「もう一文書いてください」)を足し、`chat()` を呼ぶ。
- YUTAの回答: 「user message が連続して Claude に送られるので、2文で量子計算について返答してくる」
- 評価: ほぼ正解。
  - 公式ドキュメントでは、連続する同じロールのターンは、1つのターンに結合されて、エラーにならない(下の【補足】参照)。
  - 返ってくるのは、「前の回答の続きの一文」ではない。Claude は、自分の最初の回答を見ていないので、最初から説明し直す形になる。
- 実際の出力(実機): 1段落目は、1つ目とほぼ同じ内容の説明で、2段落目に、新しい一文が付いた。予想と一致した。

### 質問2: エラーメッセージの読み解き(`ThinkingBlock` のエラー)
- 状況: 質問1を実機で動かしたとき、`AttributeError: 'ThinkingBlock' object has no attribute 'text'` が出た。
- 質問と、YUTAの回答:
  1. 最後の行は何と言っているか → 「`ThinkingBlock` は `text` フィールドを持っていない」(正解)
  2. `--->` が指す行は、何を取り出そうとしているか → 「`content` の 0 番目から `text` フィールドを取り出そうとしている」(正解)
  3. L03 の質問2との関係 → 「`text` ブロックを探して `text` を抽出する」(正解。ただし、「`type` が `"text"` のブロックを探す」と言う方が正確)
- 原因: `content[0]` が、`text` ブロックではなく、`ThinkingBlock`(モデルの思考過程を入れるブロック)だった。
- 対応: `chat()` の取り出しを、`for block in message.content:` と `if block.type == "text":` に直した(YUTAが自分で修正)。

### 質問3: 履歴にアシスタントの回答を足すと、どうなるか
- 設定: `add_assistant_message(messages, answer)` を有効にして、もう一度動かす。
- YUTAの回答: 「過去の会話での自分の回答を参照できるので、会話が続いていることが理解できる。そのため、もう一文を出力(2文ではなく)する可能性が高い」
- 評価: 正解。履歴が `user → assistant → user` の交互になることが、ポイント。
- 実際の出力(実機): 1つ目の定義に対し、新しい一文だけが返った(量子ビットと応用例を述べる文)。

## 【補足】ページ外の内容(私の整理)
- 公式ドキュメント(Messages API の Create a Message、`messages` パラメータ)に、次の記述がある。確認日 2026-10-18。出典: https://platform.claude.com/docs/en/api/messages/create
  - "Consecutive `user` or `assistant` turns in your request will be combined into a single turn."
  - つまり、同じロールが続いても、エラーにならず、1つのターンに結合される。また、モデルは、`user` と `assistant` が交互になるターンで訓練されている、とも書かれている。
- 履歴を毎回すべて送るので、会話が長くなるほど、送るトークン数が増える(料金と、コンテキストウィンドウの上限に関わる)。この点は、ページには書かれていない。私の整理で、このレッスンの範囲では、未確認。
- `content[0]` が `ThinkingBlock` になった理由は、確認できていない(確かでない)。`content` の構造(ブロックの種類が混ざる)は、L01・L03 の補足とつながる。
- 試験ガイドとの関係(私の対応づけで、公式の指定ではない): 履歴を、自分で管理して、毎回すべて送る考え方は、エージェントの会話管理(コンテキストの扱い)の土台になる。
