## 1. このレッスンの目的
仮のスコア 10 を、意味のある採点に置き換える。採点者(グレーダー)の種類と、評価基準の決め方、モデルグレーダーの実装を学ぶ。

## 2. グレーダーの種類(ページ)
グレーダーは、モデルの出力を受け取り、測定可能なフィードバック(通常は 1〜10 の数値、10 が高品質)を返す。
| 種類 | 内容 | 向く評価 |
|---|---|---|
| コードグレーダー | カスタムのロジックで、プログラム的に評価する | 出力の長さ、特定の語の有無、JSON・Python・正規表現の構文検証、読みやすさのスコア |
| モデルグレーダー | 別のモデル(別の API 呼び出し)で品質を評価する | 応答の品質、指示への従い方、完全性、有用性、安全性 |
| 人間グレーダー | 人が手動でレビューして採点する。最も柔軟だが、時間と手間がかかる | 全体的な応答品質、網羅性、深さ、簡潔さ、関連性 |

コードグレーダーの唯一の要件は、使える信号(通常は 1〜10 の数値)を返すこと。

## 3. 評価基準の定義(ページ)
グレーダーを実装する前に、明確な評価基準が必要。コード生成プロンプトの例:
| 基準 | 内容 | ページの振り分け |
|---|---|---|
| フォーマット | 説明なしで Python・JSON・正規表現のみを返す | コードグレーダー向き |
| 有効な構文 | 生成されたコードが有効な構文を持つ | コードグレーダー向き |
| タスクの遵守 | ユーザーのタスクに、正確なコードで直接対応している | 柔軟性が必要なので、モデルグレーダー向き |

## 4. モデルグレーダーの実装(ページ)
- 評価プロンプトに、タスクと解答を渡し、`strengths`(強み 1〜3)・`weaknesses`(改善点 1〜3)・`reasoning`(理由)・`score`(1〜10)を持つ JSON で返させる。
- ページのコードは、プリフィル(```` ```json ````)とストップシーケンスで JSON を取り出し、`json.loads` で辞書にする。
- 原文(後半):
  > "The key insight is asking for strengths, weaknesses, and reasoning alongside the score. Without this context, models tend to default to middling scores around 6."
  > 訳: 重要な洞察は、スコアと一緒に、強み・弱み・理由も求めること。この文脈がないと、モデルは 6 前後の無難なスコアに落ち着きがちである。
- `run_test_case` で `grade_by_model` を呼び、`score` と `reasoning` を結果に入れる。
- `run_eval` で、`statistics.mean` を使い、平均スコアを出す(プロンプト改善時に追う指標)。
  > "While model graders can be somewhat capricious, they provide a consistent baseline for measuring improvements."
  > 訳: モデルグレーダーは、多少気まぐれなことがあるが、改善を測るための、一貫したベースラインにはなる。

## 質疑(学習中の確認)
範囲: このレッスン(L13)の内容と、演習 ex09。

### 質問1: フォーマットをモデルグレーダーに任せると、何を失うか
- YUTAの回答: 「長さの数え間違いや単語発見のミス、正規表現の確かさの検証のミスなど、採点の気まぐれさが含まれるため、コードグレーダーに比べて厳格さを損なう」
- 評価: 正解。補足: ①再現性(同じ出力でも採点が変わりうる)、②費用と時間(採点ごとに追加の API 呼び出し)。機械的に確定できる事柄を、確率的なモデルに任せるのは割に合わない、という設計判断。

### 質問2: タスクの遵守をコードグレーダーで実装すると、何が難しいか
- YUTAの回答: 「明確な評価基準を設定することが難しい」
- 評価: 半分正解。評価基準が曖昧で難しいのは、モデルグレーダーでも同じ(公式ドキュメントも、LLM 採点には詳細で明確な基準を勧めている)。コードが難しい本当の理由は、基準をルールとして完全に書き下せないこと(タスク文の意味と、コードの意味の突き合わせ)。期待結果とテストコードをケースごとに用意すれば、コードで検証できるが、今のデータセットは `task` の文だけで、その手間がコストになる。

### 質問3: 切れた出力の評価は、何を測っているか(`max_tokens`)
- 状況: 3件目の採点の reasoning に、「使用例のコードが途中で切れている」とあった。
- YUTAの回答: 原因は `chat()` の `"max_tokens": 1000`。確認で、`stop_reason` が `max_tokens`、出力トークン数が 1000(上限ちょうど)だった。
- 「この評価の7〜8点は何を測っているか」→「不完全な回答の平均」。評価: ほぼ正解。正確には、切れた出力と切れていない出力が混ざった状態の品質の平均で、プロンプトの質と、テスト環境の上限の影響が区別できなくなっている。
- 直し方: 上限を上げる(捨てるもの: 費用と時間)か、プロンプトで長さを指定する(捨てるもの: 評価対象のプロンプトそのものを変えてしまう)。順番は、まずテスト環境を直してベースラインを測り直し、そのあとプロンプトを改善する。

### 質問4: 範囲確認のコード(1〜10)を足すか
- YUTAの回答: 足さない。「現状、プロンプトの指示で最大最小を守れているため。問題が発生すれば足すべき」
- 評価: 選択は許容。理由に問題がある。①根拠が 3 件のサンプルで、L09 の「3件で OK と判断する」罠と同じ形。②範囲外のスコアは、エラーにならず、平均を静かにずらす(仮の 10 を置き忘れたときと同じ構図。L12)。③L11 で、件数の指示が一度守られなかった。私なら、2 行足して静かな失敗を防ぐ。

### 質問5: 振り返り(YUTAの回答と評価)
1. f 文字列にしなかった場合、Claude に何が送られるか → 「output という文字」。評価: 部分的に正解。`{task}` と `{output}` が、波括弧付きの文字のまま入る。採点者は、実際のタスクも解答も見られないが、何らかの点数を返してしまう可能性がある(エラーにならない失敗)。
2. 採点は妥当か、冗長な出力の扱い → 「妥当だと思われます」。評価: 答えが足りない。2 件目の reasoning は「コードブロックと補足説明が付いており、『単一の JSON』の指定から逸脱」と指摘したが、score は 8。3 件とも冗長な出力で 8〜9 点だった。L11 の要件(クリーンな出力)に対しては、平均 8.33 は甘い。タスクの遵守としては妥当でも、フォーマットとしては信用できない(コードグレーダーで厳密に見る理由)。
3. reasoning などを求める理由 → 「無難な 5〜6 程度」。評価: 数字は、ほぼ合っている(原文は around 6)。理由は、ページに書かれていない。
   - 私の説明(一般的な理解。公式の記述ではない): モデルは先頭から順に生成するので、根拠を先に具体的に書かせると、それが点数の材料になり、無難な値に逃げにくい。人間にとっては、reasoning が検算の材料になり(3 件目の「`\b` の説明が不正確」という指摘の確認など)、採点者の誤解に気づけ、基準の改善と、信頼性の確認につながる。
   - 確かでない点: スキーマのキーの並び順で、生成の順序が決まるかは未確認。
4. 同じ出力を再採点するとスコアは変わるか → 「変わります。思考モデルであるため信頼性の評価もする必要があります」。評価: 結論(信頼性の評価が必要)は、公式の「まず信頼性をテストし、それから拡大する」と合っている。ただし、再採点は実際には確かめていない。変動の原因は、モデルの確率的な生成で、思考の有無とは別。再採点の実験は、実施しなかった。

## 実機での確認(YUTAの環境、2026-11-01)
- ノートブック: `exercises\ex09_Model-based-grading\model-based-grading.ipynb`(ex08 の関数を引き継ぎ、TODO とヒントを入れた課題)。新しく覚えること: 採点者を、別の API 呼び出しとして実装する(生成と採点で 2 回呼ぶ)。
- 範囲指定のエラー: スキーマの `score` に `"minimum": 1, "maximum": 10` を書いたところ、400 エラー。
  ```
  BadRequestError: ... "output_config.format.schema: For 'integer' type, properties maximum, minimum are not supported"
  ```
  - 読み解き: 構文は正しい(JSON Schema の標準の書き方)。問題は、スキーマの `integer` に `minimum`・`maximum` を書いたこと。構造化出力では、数値の最小・最大がサポートされない(L08 のノートの制約)。範囲は評価プロンプトで伝える。
- 採点側の `max_tokens=1000`: 3 回の採点呼び出しで、3 回目だけ `stop_reason` が `max_tokens`(`['thinking', 'text']`)。`JSONDecodeError: Unterminated string` になった。別の回には、`text` が `None` になり `TypeError` になったこともあった(`text` ブロックが出なかった可能性。私の推測)。構造化出力の保証は、`max_tokens` で切れると成り立たない(L08)。
- 直し方: 生成側(`chat()`)と採点側の `max_tokens` を、4000 に上げた。結果:
  | | 上限 1000(生成) | 上限 4000(生成・採点) |
  |---|---|---|
  | 平均スコア | 7.67(8、8、7) | 8.33(9、8、8) |
  | 減点の理由 | 解説の未完成、コードが途中で切れる | 形式の逸脱、説明の不正確さ |
  - 採点の `stop_reason` は 3 回とも `end_turn`。ブロックの種類は、`['thinking', 'text']`、`['text']`、`['thinking', 'text']` と変動した。
  - 注意: 0.67 点の上昇を「切れを直したから」と言い切るのは早い(3 件・1 回の実行で、生成も採点も毎回変わる)。
- 上限を上げる意味: `max_tokens` は上限で、費用は実際に生成されたトークン数で決まる(私の把握。確かでない部分がある)。生成側は、切れていた出力が最後まで出るので、実際に増える。採点側は、必要な出力が短いので、ほとんど増えず、保険の意味が大きい。
