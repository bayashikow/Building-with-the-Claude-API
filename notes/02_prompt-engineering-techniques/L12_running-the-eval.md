## 1. このレッスンの目的
評価データセットが揃ったので、評価パイプラインの中核を作る。各テストケースを取り出し、プロンプトと結合し、Claude に渡して、結果を採点する、という流れ。

## 2. 評価プロセスの流れ(ページ)
テストケースのデータセットを取得し、それぞれをプロンプトテンプレートと組み合わせ、Claude に送信して処理し、グレーダーシステムで出力を評価する。

## 3. 3つの関数(ページ)
### `run_prompt`
テストケースを受け取り、プロンプトテンプレートと結合して、Claude の出力を返す。
```python
def run_prompt(test_case):
    """Merges the prompt and test case input, then returns the result"""
    prompt = f"""
Please solve the following task:

{test_case["task"]}
"""
    messages = []
    add_user_message(messages, prompt)
    output = chat(messages)
    return output
```
- プロンプトは、わざと極めてシンプルにしてある。フォーマットの指示を含めていないため、Claude は必要以上に冗長な出力を返す可能性が高い。プロンプト設計の反復で、後ほど改善する。

### `run_test_case`
単一のテストケースの実行と、結果の採点を統括する。
```python
def run_test_case(test_case):
    """Calls run_prompt, then grades the result"""
    output = run_prompt(test_case)

    # TODO - 採点
    score = 10

    return {
        "output": output,
        "test_case": test_case,
        "score": score
    }
```
- 現時点では、ハードコードされたスコア 10。採点ロジックは、今後のセクションで取り組む。このプレースホルダーにより、**パイプライン全体をテストできる**。

### `run_eval`
評価プロセス全体を統括する。
```python
def run_eval(dataset):
    """Loads the dataset and calls run_test_case with each case"""
    results = []

    for test_case in dataset:
        result = run_test_case(test_case)
        results.append(result)

    return results
```
- データセットのすべてのテストケースを処理し、結果を1つのリストにまとめる。

## 4. 評価の実行(ページ)
```python
with open("dataset.json", "r") as f:
    dataset = json.load(f)

results = run_eval(dataset)
```
- 初回は時間がかかる。Claude Haiku を使っていても、データセット全体の処理に約30秒かかることがある。最適化の手法は、後ほど取り上げる。

## 5. 結果の確認(ページ)
`print(json.dumps(results, indent=2))` で、結果の配列を表示する。各結果は、次の3つを持つ。
| キー | 内容 |
|---|---|
| `output` | Claude からの完全な応答 |
| `test_case` | 処理された元のテストケース |
| `score` | 評価スコア(現在はハードコード) |

- フォーマット指示を与えていないので、Claude はかなり冗長な応答を生成している。これは、プロンプトの改善で対処すべき問題。

## 質疑(学習中の確認)
範囲: このレッスン(L12)の内容と、演習 ex08。

### 質問1: 仮のスコア 10 は、何のために置いてあるか
- YUTAの回答: 「採点ロジックは本レッスンの対象ではなく、後続で作成するため、現時点では採点を表す箇所はハードコードしている」
- 評価: 半分正解。これは、後回しにしている**理由**。聞いたのは、仮の値を置く**目的**。ページの趣旨は、「このプレースホルダーによって、パイプライン全体をテストできる」。採点が未完成でも、データセットの読み込み → 差し込み → 送信 → 結果の収集という流れ全体が、最後まで動くかを確かめられる。結合テストで言えば、未実装の下位モジュールを**スタブ**で置いて、上位の結合を先に確かめる方法と同じ。

### 質問2: 置き換え忘れたまま、平均を取ると何が起きるか
- YUTAの回答: 「平均は常に10となるため、たとえプロンプトの調整を行っても平均点が10となるため、版で比較することができない」
- 評価: 正解。L10 の「平均スコアで版を比べる」考え方と、正しくつながっている。
- 補足: 恐いのは**エラーにならない**こと。「平均10点=満点」は、本物の結果に見える。「3件で OK と判断する」罠(L9)と同じで、偽の安心が生まれる。設計として、仮の値を一目で偽物と分かるもの(たとえば `None`)にすれば、平均を取る段階でエラーになり、置き換え忘れに気づける。代償は、パイプライン全体のテスト時に、平均の計算まで動かせないこと(私の補足)。

### 質問3(振り返り1): プロンプトを最小にしたことで、どんな出力になったか
- YUTAの回答: 「形式の指定をしていないため、冗長な表現を含んでいる」
- 評価: 正解。具体的には、見出し(「## 実装」「## 動作確認」)、説明文、頼まれていないテストコード、が付いていた。形式の指示がないと、Claude は「役に立とうとして」周りに説明を足す(L08 の、説明文が付く問題と同じ原因)。この出力は、L11 の要件(説明やヘッダー・フッターなしの、クリーンな出力)を満たしていないが、`score` が仮の 10 なので、評価上は満点に見える。

### 質問4(振り返り2): 3つに分けるメリット、採点を変えるときの修正箇所
- YUTAの回答: 「プロンプトを変更する場合や回答の形式(output, test_case, score)の変更などが容易で、責務がわかりやすい。採点を変更する場合は、`run_test_case()` の `score` を変更する」
- 評価: 正解。変更の影響範囲が分かれている。
  | 変えたいこと | 直す場所 |
  |---|---|
  | プロンプトの文面 | `run_prompt` のみ |
  | 結果に含める項目 | `run_test_case` の戻り値 |
  | 採点 | `run_test_case` の `score` |
  | 処理の対象や順序 | `run_eval` |
- 設計書で言えば、機能ごとにモジュールを分けて、変更時の影響を局所化する考え方と同じ。

## 実機での確認(YUTAの環境、2026-10-25)
- ノートブック: `exercises\ex08_Running-the-eval\running-the-eval.ipynb`(ex06 のセットアップとヘルパーを引き継ぎ、TODO とヒントを入れた課題)。新しく覚えること: 3つの関数を組み合わせて、全件を処理する。
- `dataset.json` は、ex07 のフォルダにあるものを、相対パス(`../ex07_Generating-test-datasets/dataset.json`)で読んだ。
- TODO 1〜5 は、すべて正しく書けた。3件を処理できた。
- 1件目(S3バケット名の検証)の `output`: 「## 実装」という見出しとコードブロックに加えて、「## 動作確認」のテストコードまで付いた、冗長な出力。
- `encoding` を付けない場合の実行(YUTAが試した):
  ```
  UnicodeDecodeError: 'cp932' codec can't decode byte 0x83 in position 31: illegal multibyte sequence
  ```
  - 読み解き: 最後の行は、「cp932 の規則でバイトを文字に変換(decode)しようとしたが、規則に合わないバイトがあった」と言っている。
  - YUTAの回答: 「cp932 で読もうとしたが、decode できないので `UnicodeDecodeError` である」→ 流れは正しい。語の意味は、次の表。
    | 語 | 意味 |
    |---|---|
    | `cp932` | Windows の日本語環境で使われる文字コード(Shift_JIS の仲間) |
    | `decode` | ファイルの中身(バイトの並び)を、文字に変換すること |
    | `UnicodeDecodeError` | その変換に失敗したときのエラー |
  - `--> 293 ... fp.read()` の行が、エラーの場所を指している。YUTAの回答「`open()` で開くことは問題ないが、`json.load` で中身を読み込んだときにエラーが起きる」→ 正解。`open()` は、ファイルを開くだけで、文字への変換は `read()` のときに行われる。
  - 起きたことの全体: ①ex07 で `encoding="utf-8"` を付けて保存した(UTF-8)→ ②ex08 で `encoding` なしで読んだ → 環境の既定(cp932)で読もうとした → ③UTF-8 の日本語のバイトは、cp932 の規則では不正な並びになり、失敗した。
- 学び: ページのコードは、既定が UTF-8 の環境(Mac や Linux)なら動く。日本語を含むファイルは、読み書きの両方で、`encoding="utf-8"` を付ける習慣が安全。

## 【補足】ページ外の内容(私の整理)

- 今回の評価パイプラインは、L10 の5ステップのうち、ステップ3(Claude に通す)とステップ4(採点者に通す)の枠にあたる。ステップ4は、仮の値。
