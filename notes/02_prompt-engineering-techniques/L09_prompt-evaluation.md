## 1. このレッスンの目的
良いプロンプトを書くだけでは、信頼できる AI アプリケーションにはならない。プロンプトエンジニアリングと、プロンプト評価の違いを理解し、なぜ評価が必要かを知る。

## 2. プロンプトエンジニアリング対プロンプト評価
| | プロンプトエンジニアリング | プロンプト評価 |
|---|---|---|
| 焦点 | 効果的なプロンプトを作る技術のツールキット | 自動テストで、プロンプトの効果を測る |
| 例 | マルチショットプロンプティング、XMLタグによる構造化、その他のベストプラクティス | 期待される回答に対してテストする / 同じプロンプトの異なる版を比較する / 出力をレビューしてエラーを確認する |
| 役割 | Claude が、求めていることと、応答の仕方を、正確に理解できるようにする | プロンプトが、実際にどれだけうまく機能しているかを測る |

## 3. プロンプトを書いたあとの3つの道
| 選択肢 | 内容 | ページの評価 |
|---|---|---|
| 1 | プロンプトを一度テストして、十分に良いと判断する | ユーザーが予期しない入力をしたとき、本番で破綻する重大なリスク |
| 2 | 数回テストして、1〜2個のコーナーケースに対応するよう調整する | 1よりは良いが、ユーザーは、想定していなかった非常に予期しない入力をしてくる |
| 3 | 評価パイプラインに通してスコアを付け、客観的な指標でプロンプトを反復改善する | より多くの作業とコストが必要だが、信頼性への確信がはるかに高まる |

## 4. なぜ、多くのエンジニアがテストの罠に陥るのか
- 選択肢1と2は、筆者自身も含めて、すべてのエンジニアが陥りやすい罠。
- 理由: 実際のユーザーが出会うエッジケースの多さを、過小評価しがち。
- 本番にデプロイすると、ユーザーは、予想もしなかった方法で対話する。限られたテストでは堅実に見えたプロンプトも、実世界の入力の多様性に直面すると、すぐに破綻することがある。

## 5. 評価優先のアプローチ(選択肢3)
評価パイプラインで、広いテストケースにわたる客観的な指標が得られる。これにより、次のことができる。
- 本番の問題になる前に、弱点を特定する。
- 異なるプロンプトの版を、客観的に比較する。
- 測定可能な改善に基づいて、自信を持って反復改善する。
- より信頼性の高い AI アプリケーションを作る。

代償: 時間とテスト基盤への、事前投資が必要。目標は、ユーザーが問題に遭遇したあとではなく、開発中に問題を見つけること。

## 質疑(学習中の確認)
範囲: このレッスン(L09)の内容。

### 質問1: 請求書の金額抽出を、3件で試して全部成功した。どの選択肢に当たり、最大のリスクは何か
- 設定(私の出した問題): 請求書から金額を抽出するプロンプトを書き、手元の3件で試して、すべて正しく抽出できた。このままリリースする。
- YUTAの回答: 「選択肢2。ユーザが予期しない入力に対応しきれない」
- 評価:
  - 選択肢の判定: 私の問題文があいまいだった。「数回試して調整する」が2、「一度試して十分と判断」が1で、今回は、調整なしで終えているため、1にも2にも読める。2で正解として扱った。
  - リスク: 方向は正しいが、ページの言葉に近く、具体性が足りない。足りない点は2つ。
    1. 何が予期しないのか(税込と税抜の併記、金額が複数、外貨建て、金額欄が空、など)。手元の3件は、自分が思いつく範囲から選んだ標本で、偏っている。
    2. 失敗率を測っていないこと。3件成功しても、本番で10%壊れるのか、0.1%なのか、わからない。プロンプトを直したとき、以前うまくいったケースが壊れても、気づけない(結合テストで言う、回帰テストがない状態)。

### 質問2: 選択肢3の評価を始めるのに、最低限、何を用意するか
- YUTAの回答: 「予想されるユーザ入力を詳細に調査してテストケースを作成し、各テストケースに対して評価を行う。また、失敗する確率なども把握して、基準値に達しているかを確認する。達しない場合は再度調整を行い再テストする」
- 評価(L10 を読む前): 評価の流れは、的確。特に、失敗率を基準値と比較する点は、選択肢3の核心を押さえている。
- 当初の私の指摘(L10 を読む前): 「期待値(正解データ)」と「合否基準を先に決めること」が足りない、と指摘した。
- **L10 を読んだあとの修正(私の指摘の誤り)**:
  - L10 の例では、採点者(grader)が、元の質問と Claude の回答の両方を見て、1〜10 で採点する。**ケースごとの正解データ(期待値)は、使っていない**。そのため、「期待値がないと評価できない」という私の言い方は、強すぎた。正解データとの照合は、評価の方法の1つ(L9 本文の「期待される回答に対してテストする」)であって、必須条件ではない。
  - L10 の例は、**平均スコアで版を比較する**(7.66 → 8.7 など)。「合格のしきい値(基準値)を先に決める」という手順は、ページには書かれていない。基準値を先に決める方針は、私の補足(結果を見てから基準を決めると、都合よく合格にできる、という考え)で、実務では有効だが、ページの内容ではない。
  - **YUTAの回答に足りなかった要素**: 「採点者(grader)」。ケース(データセット)と、採点する仕組みがそろって、評価になる。
  - YUTAの流れ(ケース作成 → 評価 → 数値化 → 調整して再テスト)は、L10 の5ステップ(プロンプト作成 → データセット作成 → Claude に通す → 採点者に通す → 変更して繰り返す)と、ほぼ一致していた。

## 【補足】ページ外の内容(私の整理)
- 評価を結合テストにたとえると、データセットがテストケース、採点者が合否判定(期待結果との照合)にあたる。ただし、プロンプトの出力は、実行ごとに少し変わるため、1件の合否より、全体のスコアの傾向を見る(私の例えで、ページにはない)。
- 再テストは、同じデータセットで行う(ケースが変わると、版の比較にならない)。そのデータセットに合わせすぎた調整は、本番で崩れる可能性がある(私の補足)。
- 試験ガイドとの関係: ガイドの全文を検索したが、このレッスンを直接扱う項目は、確認できなかった(「評価」にあたる語は、自己評価パターンなど、断片的な箇所にしか出てこない)。優先度は低めと見るが、確定ではない。
