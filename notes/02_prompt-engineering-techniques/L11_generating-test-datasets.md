## 1. このレッスンの目的
カスタムのプロンプト評価ワークフローを作る第一歩として、評価用のテストデータセットを、コードで自動生成する方法を学ぶ。

## 2. 目標の設定(ページ)
AWS 特有のコードを書くユーザーを支援するプロンプトの評価システムを作る例。プロンプトに期待する出力は、次の3種類。
- Python コード
- JSON 設定ファイル
- 正規表現

重要な要件: ユーザーがタスクの支援を求めたとき、**余分な説明、ヘッダー、フッターなしで**、これらの形式のいずれかで、クリーンな出力を返すこと。

プロンプト(バージョン1):
```python
prompt = f"""
Please provide a solution to the following task:
{task}
"""
```

## 3. 評価データセットの作成(ページ)
- データセットには、プロンプトに入力する入力データが含まれる。プロンプトと入力の各組み合わせについて、プロンプトを実行し、結果を分析する。
- 形: JSON オブジェクトの配列。各オブジェクトは、Claude に達成してほしいことを記述する `task` プロパティを持つ。
- 手動で作ることも、Claude で自動生成することもできる。
- テストデータの生成は、フルサイズのモデルの代わりに、**Haiku のような高速なモデルを使う好機**。

## 4. コードによる生成(ページ)
ヘルパー関数は、L04〜L08 のものに、`temperature` と `stop_sequences` を足した `chat()`。

`generate_dataset()` の流れ:
1. 生成用のプロンプトを書く。「Python、JSON、または正規表現を書くことで解決できる、AWS 関連のタスクを、JSON オブジェクトの配列として生成する」。
   - 出力例(`task` を持つ配列)を示す。
   - 絞り込みの指示: 「単一の Python 関数、単一の JSON オブジェクト、または単一の正規表現で解けるタスクに絞る」「書くコードが多くないタスクに絞る」。
   - 「3件生成する」。
2. ```` ```json ```` のプリフィルと、```` ``` ```` のストップシーケンスで、JSON を取り出す。
3. `json.loads(text)` で、Python のリストにする。

実行例: `dataset = generate_dataset()` で、Python 関数、JSON 設定、正規表現のタスクが、3件返る。

## 5. データセットの保存(ページ)
```python
with open('dataset.json', 'w') as f:
    json.dump(dataset, f, indent=2)
```
- 後の評価で簡単に読み込めるように、ノートブックと同じディレクトリに、`dataset.json` として保存する。

## 現行の方法(YUTAの ex07 で実施した形)
構造化出力で、プリフィルとストップシーケンスを置き換える。詳細は L08 のノートを参照。
- スキーマは、一番外側を `object` にして、その中の `tasks` に配列を入れる形にした(下の質疑5と【補足】を参照)。
  ```python
  schema = {
      "type": "object",
      "properties": {
          "tasks": {
              "type": "array",
              "items": {
                  "type": "object",
                  "properties": {"task": {"type": "string"}},
                  "required": ["task"],
                  "additionalProperties": False,
              },
          },
      },
      "required": ["tasks"],
      "additionalProperties": False,
  }
  ```
- `create()` に `output_config={"format": {"type": "json_schema", "schema": schema}}` を渡す。
- 本文は、`type` が `"text"` のブロックを探して取り出し、`json.loads()` で辞書にして、`data["tasks"]` の配列だけを返す。

## 質疑(学習中の確認)
範囲: このレッスン(L11)の内容と、演習 ex07。

### 質問1: データセット生成に高速なモデルを使うのは、なぜ許容されるか。何を捨てているか
- YUTAの回答: 「高度な思考が必要なタスクではないため。捨てているのは、データセットの品質」
- 評価:
  - 前半: 「高度な思考が不要」は、疑問が残る。ページには、この理由は書かれていない(「テストデータを生成しているため」としかない)。多様で現実的なテストケースを作るのは、単純な作業ではない。許容できる理由として妥当なのは、①生成する `task` が短い文で要求が軽い、②件数が多くなり得るので速度と費用の差が効く、③生成物は評価の入力であって、本番の成果物ではなく、確認して作り直せる、の3点(私の考察)。
  - 後半: 方向は正しいが、広すぎる。具体的には、多様性(似たタスクばかりになる)、網羅性(境界ケースが入らない)、現実性(不自然なタスクになる)、正確さ(条件が矛盾する)。データセットの品質が低いと、その上の評価のスコアが、すべて信用できなくなる(結合テストで言えば、テストケース自体の設計がずさんな状態)。

### 質問2: スキーマは、件数を決めているか(演習で2件が返ったあと)
- 状況: 「3件生成してください」と書いたのに、2件(Python と JSON。正規表現なし)が返った。`stop_reason` は `end_turn`。
- YUTAの回答: 「件数については決めていません」
- 評価: 正解。`end_turn` から、`max_tokens` による切れや、拒否(`refusal`)ではなく、Claude が自分で2件で終えたと分かる。

### 質問3: なぜ2件になったか
- YUTAの回答: 「Claude のプロンプトを解読する能力が低い」
- 評価: 根拠が足りない。観察は1回だけで、1回の結果から能力を結論づけられない。指示ははっきり書かれていた。押さえる点は、**プロンプトの指示は、守られることが多いが、保証ではない**(スキーマの制約は、形を強制する)。本当の原因は、確かでない。

### 質問4: 正規表現が1件もないデータセットは、何が問題か
- YUTAの回答: 「十分なデータセットを得られていないので、評価ができない」
- 評価: 方向は合うが、言い切りすぎ。評価自体は実行できる。問題は、評価結果が何を代表するかで、正規表現の弱さが評価で見つからず、平均スコアは「Python と JSON について」の数字になる。L9 の「3件で OK と判断する」罠と同じ構図(偏った標本による、偽の安心)。

### 質問5(YUTAから): なぜ一番外側を `object` にして `tasks` に配列を入れたのか
- 回答: 構造化出力のルートに配列を使えるかを、私が確認しておらず、安全側に倒したため。
- 確認結果(公式ドキュメント、下の【補足】): ルートが `object` でなければならないかは、ページに書かれていない(ページの例は、すべてルートが `object`)。ルートの配列が使えるかは、公式からは確定できない(確かでない)。
- 設計としての利点と代償:
  | 利点 | あとで項目(`category` など)を足しても、形を変えずに済む。ルートの配列が使えるかという不確かさを避けられる |
  |---|---|
  | 代償 | 取り出しの処理(`data["tasks"]`)が1つ増える。ページの形と違うため、読み替えが要る |
- 評価を実行する側への影響: 取り出しの処理は `generate_dataset()` の中に閉じ込めた。保存した `dataset.json` は、配列のまま(ページと同じ形)なので、読み込む側に影響しない。

### 質問6: 振り返り(YUTAの回答と評価)
1. 多様性・現実性: 「1件目が、正規表現と Python の混在で、境界があいまい」→ 正解。ただし、これは1回の生成結果についての指摘で、実行のたびにデータの質が変わる。
2. object で包む影響: 「取り出す処理が必要」→ 正解(上の補足あり)。
3. 件数の保証: 「しなかった。保証する仕組みが必要」→ 正解。
4. 高速なモデルで捨てたもの: 「確かめられた。プロンプトの指示に従わず2件を出力した」→ 言い切りすぎ。観察は1回で、比較対象(より大きなモデルで、同じプロンプト)がない。確かに言えるのは、「Haiku で、指示が守られない例が1つ見えた」まで。厳密には、モデルだけを変えて、同じプロンプトを何回か比べる必要がある(L9〜L10 の評価の考え方)。

## 実機での確認(YUTAの環境、2026-10-24)
- ノートブック: `exercises\ex07_Generating-test-datasets\generating-test-datasets.ipynb`(ex06 のセットアップとヘルパーを引き継ぎ、TODO とヒントを入れた課題)。新しく覚えること: 複数件のデータを、スキーマで表す。
- 1回目の生成(元のプロンプト「3件生成してください」): 2件(Python と JSON)。`stop_reason` は `end_turn`。
- プロンプトの変更: 「3件」を、「Python・JSON・正規表現を各1件ずつ必ず作成してください。(全3件)」に変更。件数だけでなく、内訳を明示した。結果: 4回続けて3件(1回目の確認と、あと3回)。
- ただし、4回の成功は、毎回3件になる保証ではない。
- 生成された `task` の例(別々の実行):
  - 正規表現を使って S3 のキーから日付を抽出する Python 関数(Python と正規表現の境界があいまい)。
  - Lambda の設定を表す JSON(CloudFormation の形式)。
  - ARN を検証する正規表現。
- 件数のチェックと再試行を、コードで追加した。最終形(YUTAが書いたもの):
  ```python
  counter = 0

  while len(dataset) != 3:
      print("3件ではないため、再度生成します。")
      dataset = generate_dataset()
      print(dataset)
      print(len(dataset))
      counter += 1
      if counter >= 4:
          print("5回試したが、3件にならなかった。")
          raise Exception("3件にならなかった。")
          break

  print(counter+1, "回で3件になった。")
  ```
  - 修正の過程: ①外側の `if` が冗長 → `while` のみに、②`< 3` だと 4件以上が通る → `!= 3` に、③上限なしだと API を呼び続けて料金が膨らむ → カウンターで上限、④`print` と `break` だけだと次のセルに進める → `raise` で止める、⑤回数の数え方(最初の1回 + 再生成 4回 = 5回)を自分の計算で合わせた。
  - 小さな改善点: `raise` の次の `break` には到達しない。`Exception` より、具体的なエラーの種類(`RuntimeError` など)のほうが良い。
  - 上限に達して `raise` される場面は、まだ動かして確認していない(件数の条件を、一時的に満たせない値にして試す方法がある)。
- 設計上の学び: 再生成は、「失敗の頻度という情報」を見えなくしてしまう。評価の用途では、何回失敗したかも記録したほうが良い(L9 の、失敗率を把握する話)。

## 【補足】ページ外の内容(私の整理)
### 公式ドキュメント: 構造化出力のスキーマの制約
出典: https://platform.claude.com/docs/en/build-with-claude/structured-outputs (「JSON Schema limitations」)。確認日 2026-10-24。以下は私による要約。
- ルートが `object` でなければならないか、ルートの配列が使えるか: ページには書かれていない。ページの例は、すべてルートが `object`(確かでない)。
- 配列の件数の制約: `minItems` は 0 か 1 のみサポート。それ以外の配列の制約は、サポートされない。`maxItems` は名前では出てこないが、「それ以外」に当たると読める(確定ではない)。
- そのため、「ちょうど3件」をスキーマで指定することは、できないようだ。件数の保証は、プロンプトの工夫と、コード側の確認(件数のチェックと再試行の上限)に頼る。

### 設計の整理(私の補足)
- 生成したデータセットは、人間が一部を目で確認する(特に、種類の偏りと、境界のあいまいなタスク)。
- 同じプロンプトでも、実行のたびに質が変わるため、データセットは一度作って、保存して、使い回す(`dataset.json`)。評価で版を比べるときは、同じデータセットを使う(L9 の補足)。
- 生成用のモデルと、あとで評価対象にするモデルを、同じにするかは、ページには書かれていない。
