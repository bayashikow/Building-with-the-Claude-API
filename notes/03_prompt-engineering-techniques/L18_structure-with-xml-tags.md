## 1. このレッスンの目的
データを多く含むプロンプトで、指示とデータ、異なる種類のデータの境界を、XMLタグで明確にする方法を理解する。

## 2. なぜ構造が必要か(ページ)
- 多くのコンテンツを含むプロンプトでは、Claude は、どのテキストが一緒に属しているのか、各セクションが何を表すのかを理解するのに苦労することがある。
- 例: 20ページの売上記録を分析させる場合、明確な境界がないと、指示と分析対象のデータを区別しづらい。
- 対処: 売上記録を `<sales_records>〜</sales_records>` のようなタグで囲み、明確な区切りを作る。

## 3. 実践例: コードとドキュメント(ページ)
- 提供したドキュメントを使ってコードをデバッグさせる場合、すべてを混ぜると、何がコードで何がドキュメントか、ほぼ判別できない。
- 改善版は、`<my_code>` と `<docs>` で境界を作る。

## 4. カスタムタグ名(ページ)
- 正式なXMLタグを使う必要はない。内容に合った**説明的な名前**を自分で付ける。
  | タグ | 役割 |
  |---|---|
  | `<sales_records>`(`<data>` より良い) | 何のデータかが分かる |
  | `<athlete_information>` | ユーザーの詳細を明確に識別する |
  | `<my_code>` と `<docs>` | 異なる種類のコンテンツを分離する |
- タグ名が具体的で説明的なほど、Claude は各セクションの目的を理解しやすい。

## 5. 使うタイミング(ページ)
- 大量のコンテキストやデータを含める場合
- 異なる種類のコンテンツ(コード・ドキュメント・データ)を混在させる場合
- コンテンツの境界について、特に明確にしたい場合
- 複数の変数を差し込む、複雑なプロンプトの場合
- 短いコンテンツでも、構造を明確にする区切りとして役立つ。

## 6. 実際の応用(ページ)
```
<athlete_information>
- Height: 6'2"
- Weight: 180 lbs
- Goal: Build muscle
- Dietary restrictions: Vegetarian
</athlete_information>

Generate a meal plan based on the athlete information above.
```
- 身長・体重・目標・制限が、すべて関連するアスリートのデータで、一緒に考慮すべきものだと明確になる。
- シンプルなプロンプトでは劇的な改善が見られないこともある。プロンプトが複雑で、多様で大量のコンテンツを含むほど、XMLタグの価値が増す。

## 質疑(学習中の確認)
範囲: このレッスン(L18)の内容。

### 質問1: 契約書とレビュー観点を渡すとき、最も適切な構成はどれか
出題: 契約書の全文(約30ページ)と、確認してほしい観点のリストを渡して、リスクを指摘させる。プロンプトの構成として最も適切なのは。
- A: 指示、観点、契約書の全文を、改行だけで続けて書く。
- B: 契約書の全文を `<data>` で囲み、観点を `<data>` で囲み、指示を最後に書く。
- C: 契約書の全文を `<contract>`、観点を `<review_points>` で囲み、それぞれを参照する指示を書く。
- D: 契約書が長いので、XMLタグは使わず、短く要約してから渡す。
- YUTAの回答: C(「どこまでが契約書本文で、どこからが観点であるかを明瞭にできる」)
- 評価: 正解。理由も合っている。
  - C が正しい理由: 別々のタグで囲むと境界が明確になる。タグ名が内容を表すので、指示の側から「`<contract>` を `<review_points>` の観点で確認して」と参照できる。
  - A: 境界がなく、指示・観点・本文の区別がつかない。
  - B: 区切りはあるが、2つとも同じ `<data>` で、どちらが何か区別できない。ページの「`<data>` より `<sales_records>`」の注意と同じ。
  - D: 要約すると、リスクに関わる細部が落ちるおそれがある。長さの問題は、構造化で対処できる。
- 補足: 「指示は最後に書く」のような配置は、ページに書かれていない。長い資料の配置は、別のレッスンで出てくる可能性がある(確かでない)。

## 【補足】ページ外の内容(私の整理)
- これまでの手作りのプロンプト(ex09 のモデルグレーダーなど)では、`タスク: {task}`、`解答: {output}` のように、ラベルだけで区切っていた。解答に長いコードが入ると、どこまでが解答か曖昧になる。`<answer>〜</answer>` のように囲むほうが安全(私の整理)。
- タグ名は、API が定義した名前ではない。プロンプトの中だけで意味を持つので、自分で決めてよい。
- 設計書で言えば、入力データと処理の指示を、別の項目に分けて書くことに近い。
- このページには、スコアの変化を示す数値はない。効果は、複雑なプロンプトで大きくなる、という説明。
- 試験ガイドとの関係: ガイドの全文を検索したが、このレッスンを直接扱う項目は、確認できなかった。プロンプトの書き方の基本にあたり、対応づけは私の判断(公式の指定ではない)。
