## 1. このレッスンの目的
入力/出力のサンプルペアをプロンプトに入れて応答を導く手法(one-shot / multi-shot)と、効果的な例の作り方を理解する。

## 2. 例の仕組み(ページ)
- 例の提供は、最も効果的なプロンプトエンジニアリング技術の一つ。「one-shot」または「multi-shot」プロンプティングと呼ばれ、Claude に入力/出力のサンプルペアを与えて、応答を導く。
- 題材: ツイートのポジティブ/ネガティブ分類。課題は**皮肉**。「ああ、そうだね、『プラン9・フロム・アウタースペース』以来、最高の映画だったよ」は、表面上はポジティブだが、実際は皮肉でネガティブ(プラン9は、史上最悪の映画の一つとして有名)。

## 3. コーナーケースへの対処(ページ)
改善したプロンプトに含めるもの:
| 要素 | 内容 |
|---|---|
| 明確なポジティブの例 | 「今夜の試合は最高だった!」→「ポジティブ」 |
| 皮肉の例 | 「ああ、今夜はフライトの遅延が本当に必要だったよ!最高だね!」→「ネガティブ」 |
| コンテキスト | 皮肉を慎重に扱うべき理由の説明 |

- 例は `<sample_input>`・`<ideal_output>` のような XML タグで囲む。各部分が何を表すかが、Claude に明確になる(L18)。

## 4. 例を使うべき場面(ページ)
- コーナーケースやエッジシナリオを捉える
- 複雑な出力形式(特定のJSON構造など)を定義する
- 求める正確なスタイルやトーンを示す
- 曖昧な入力の処理方法を示す

## 5. One-shot と Multi-shot(ページ)
| 種類 | 内容 |
|---|---|
| One-shot | パターンを確立するために、単一の例を提供する |
| Multi-shot | さまざまなシナリオをカバーするために、複数の例を提供する |

- さまざまなエッジケースに対応する場合や、異なるタイプの有効な応答を示したい場合は、multi-shot を使う。

## 6. 評価から良い例を見つける(ページ)
- プロンプト評価を実行するとき、最も高いスコアの出力を探し、例として使う。
- 10点(または利用可能な最高スコア)を獲得した応答の、入力/出力ペアを、プロンプト内の例にする。特定のユースケースでの「完璧な」出力が、Claude に伝わりやすくなる。

## 7. 例にコンテキストを追加する(ページ)
入力/出力のペアに加えて、**なぜその出力が良いのか**を説明する。
```
<ideal_output>
[Your example output here]
</ideal_output>

This example is well-structured, provides detailed information
on food choices and quantities, and aligns with the athlete's
goals and restrictions.
```
訳: この例は、構造が整っていて、食品の選択と分量について詳細な情報を示し、アスリートの目標と制限に合っている。
- Claude が、形式だけでなく、良い応答の背後にある理由を理解する助けになる。

## 8. ベストプラクティス(ページ)
1. 常に XML タグを使って、例を明確に構造化する。
2. 何を示しているかを明示する(例: 「これは理想的な応答を伴う入力例です」)。
3. 最も一般的な失敗ケースに対応する例を含める。
4. なぜその例の出力が理想的と考えられるのかを説明する。
5. 例を、特定のタスクに関連性のあるものに保つ。

- 例は「語るのではなく示す」点で強力。求めるものを言葉で正確に説明する代わりに、直接示す。プロンプトの信頼性が大幅に向上し、指示だけでは表しにくい微妙な要件を、Claude が理解しやすくなる。

## 質疑(学習中の確認)
範囲: このレッスン(L19)の内容。

### 質問1: 混在レビューの誤分類を直すには、何をするか
出題: 商品レビューを「ポジティブ/ネガティブ/中立」に分類するプロンプトで、「褒めつつ不満を述べる」混在のレビューの誤分類が目立った。最も適切な改善は。
- A: 「正確に分類してください」と、指示を強めて書く。
- B: 混在レビューの入力と、正しい分類、その理由の説明を例として足し、`<sample_input>`・`<ideal_output>` で囲む。
- C: 評価データセットから、混在レビューを除いて、スコアを上げる。
- D: 例として、明確にポジティブなレビューだけを、10個足す。
- YUTAの回答: B(「例示をすることで Claude が判断を行いやすくなるため」)
- 評価: 正解。理由は方向が合っている。より正確に言うと、「どの種類のケースが難しいかを、例が具体的に示している」。指示では表しにくい微妙な基準(褒めと不満の比重の扱い)を、「語るのではなく示す」ことで伝えられる。
  - B が正しい理由: 失敗しているのは混在レビューというコーナーケース。ページの「最も一般的な失敗ケースに対応する例を含める」にあたる。入力・正しい分類・理由を示し、タグで役割も明確にする。
  - A: 「正確に」は、すでに期待されていることで、新しい情報を与えない。何をもって正確とするかは、変わらない。
  - C: 失敗するケースを評価から除くだけで、スコアは上がっても、実際の性能は上がらない(L15 の「測る物差しを変えない」と同じ問題)。
  - D: 明確なポジティブは、すでにできている部分で、失敗ケースに効かない。ポジティブの例ばかりだと、偏りが生じるおそれがある(私の整理)。

## 【補足】ページ外の内容(私の整理)
- L09〜L14 の評価と、L18 の XML タグが、ここでつながる。評価で高得点だった出力を、`<sample_output>` として次の版のプロンプトに入れる流れ(ページの趣旨)。
- 例の数が多いと、入力が長くなり、費用と処理時間が増える可能性がある。また、例に偏ると、似た出力ばかりになるおそれがある。いずれもページには書かれていない(確かでない)。
- 評価データセットの入力を、そのまま例に使うと、同じ入力で評価することになり、成績が実際より良く見える可能性がある(試験用の問題を、学習にも使うのと同じ)。例と評価データは分けるほうが安全(私の整理)。
- 設計書で言えば、仕様の文章だけでなく、入出力の具体例(テストケース)を添えることで、解釈のずれを防ぐのに近い。
