## 1. このレッスンの目的
プロンプトエンジニアリング(作成したプロンプトを、より信頼性が高く、高品質な出力が得られるよう改善すること)の進め方を理解する。基本のプロンプトから始め、評価し、手法を適用して改善する、という反復のプロセス。

## 2. 反復的改善プロセス(ページ)
| 順 | ステップ | 内容 |
|---|---|---|
| 1 | 目標を設定する | プロンプトで達成したいことを定義する |
| 2 | 初期プロンプトを書く | 基本的な最初の試みを作る |
| 3 | プロンプトを評価する | 基準に対してテストする |
| 4 | 手法を適用する | パフォーマンスを改善する特定の手法を使う |
| 5 | 再評価する | 変更によって実際に結果が改善したかを確認する |

- 満足できるパフォーマンスになるまで、ステップ4〜5を繰り返す。各反復で、評価スコアに測定可能な改善が見られるはず。

## 3. 評価パイプラインの構築(ページ)
- 題材: アスリート向けの1日分の食事プランを生成するプロンプト。入力は、身長・体重・目標・食事制限。
- 評価のセットアップは、`PromptEvaluator` クラスを使う(データセット生成とモデルによる採点を処理する)。
  ```python
  evaluator = PromptEvaluator(max_concurrent_tasks=5)
  ```
  - `max_concurrent_tasks` は、並行処理数。レート制限エラーを避けるため、低い値(3など)から始める。APIクォータが許せば、増やして高速化できる。

### テストデータの生成
```python
dataset = evaluator.generate_dataset(
    task_description="Write a compact, concise 1 day meal plan for a single athlete",
    prompt_inputs_spec={
        "height": "Athlete's height in cm",
        "weight": "Athlete's weight in kg",
        "goal": "Goal of the athlete",
        "restrictions": "Dietary restrictions of the athlete"
    },
    output_file="dataset.json",
    num_cases=3
)
```
- プロンプトに必要な入力を定義すると、要件に基づいてテストケースを自動生成する。
- 開発中は、反復サイクルを速めるため、テストケースを少なく(2〜3個)保つ。最終検証で増やす。

### 初期プロンプト(ベースライン)
```python
def run_prompt(prompt_inputs):
    prompt = f"""
What should this person eat?

- Height: {prompt_inputs["height"]}
- Weight: {prompt_inputs["weight"]}
- Goal: {prompt_inputs["goal"]}
- Dietary restrictions: {prompt_inputs["restrictions"]}
"""
    messages = []
    add_user_message(messages, prompt)
    return chat(messages)
```
- 意図的に素朴な文面。おそらく低品質な結果になるが、改善を測る出発点になる。

### 評価基準の追加
```python
results = evaluator.run_evaluation(
    run_prompt_function=run_prompt,
    dataset_file="dataset.json",
    extra_criteria="""
The output should include:
- Daily caloric total
- Macronutrient breakdown
- Meals with exact foods, portions, and timing
"""
)
```
- 採点モデルが考慮する追加の基準を指定できる。ユースケースに重要な要件に対して、評価される。

## 4. 結果の分析(ページ)
- 評価を実行すると、数値スコアと、詳細な HTML レポートが得られる。レポートには、各テストケースの実行内容が、各スコアに対するモデルの推論つきで示される。
- 初期スコアが低くても、落胆しない。**10点中2.3点は、最初の試みとして典型的**。目標は、手法を適用するにつれて、一貫した改善が見られること。
- レポートは、どこで失敗しているか、どんな改善が必要かの把握に使い、次の反復の方向を決める。

## 5. 次のステップ(ページ)
ベースラインが確立できたら、特定の手法を適用する。**一度に1つの変更を行い、その影響を評価し、うまくいったことの上に積み重ねる**。この体系的な進め方で、自分のユースケースに最も価値のある手法が分かる。

## 質疑(学習中の確認)
範囲: このレッスン(L15)の内容。

### 質問1: ベースラインが 2.3 のとき、次の進め方はどれか
出題: 平均が 2.3 のとき、次の改善の進め方として最も適切なのは。
- A: 形式・役割・出力例を、まとめて1回で足し、再評価する。
- B: レポートで最も低い項目に効きそうな変更を1つだけ足し、同じデータセットで再評価する。
- C: データセットを減らして、点が高く出るケースにそろえる。
- D: 再評価せず、次の手法の学習に進む。
- YUTAの回答: B(理由の記載はなかった)
- 評価: 正解。
  - B が正しい理由: 変更を1つに絞り、同じデータセットで再評価すると、点の変化をその変更の効果として読める。ページの「一度に1つの変更を行い、その影響を評価する」にあたる。
  - A: 点が上がっても、どの変更が効いたか分からない。下がった場合も、どれが悪さをしたか分からない。複数の不具合を同時に直して、原因が切り分けられない状況と同じ。
  - C: 測る物差しを変えると、前後の比較が成り立たない(L10 の「再テストは同じデータセットで」)。
  - D: 改善したかを数値で確かめられない。サイクルの⑤(再評価)を飛ばすと、評価パイプラインの意味がなくなる。
- 補足: 1つの変更でも、点は1回ごとに1点程度ぶれる(ex10 で確認)。差が小さいときは、件数を増やして確かめる。
