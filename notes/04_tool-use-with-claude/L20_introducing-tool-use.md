## 1. このレッスンの目的
ツール使用が解決する課題と、アプリケーションと Claude の間の基本的な往復の流れを理解する。

## 2. ツールがない場合の問題(ページ)
- ツールは、Claude が外部世界から情報にアクセスできるようにし、訓練中に学習した内容を超えて能力を拡張する。
- デフォルトでは、Claude は訓練データからの情報のみを知っている。最新のイベント、リアルタイムデータ、外部システムにはアクセスできない。
- 例: 「サンフランシスコの天気は?」と聞かれても、「最新の天気情報にアクセスできません」としか答えられない。リアルタイムデータが必要な利用者にとって、不満の残る体験になる。
- ツール使用は、Claude が新しい情報を要求し、受け取るための、**構造化された方法**を作ることで、この制限を解決する。

## 3. ツール使用の仕組み: 4ステップの往復(ページ)
| # | ステップ | 担当 | 内容 |
|---|---|---|---|
| 1 | 初期リクエスト | アプリ → Claude | 質問を、外部ソースから追加データを取得する方法の指示とともに送る |
| 2 | ツールリクエスト | Claude → アプリ | 質問を分析し、追加情報が必要と判断し、必要なデータの具体的な詳細を要求する |
| 3 | データ取得 | アプリ(サーバー) | コードを実行し、外部APIやデータベースから、要求された情報を取得する |
| 4 | 最終応答 | アプリ → Claude | 取得したデータを送り返し、Claude が元の質問と新しいデータの両方を使って、完全な応答を生成する |

### 天気の例(ページ)
利用者が現在の天気を尋ねる → 天気データを取得する方法の指示をプロンプトに含める → Claude が最新の情報が必要と認識し、特定の場所の天気データを要求する → サーバーが天気APIを呼び出してリアルタイムの状況を取得し、Claude に送り返す → Claude が、新しい天気データと質問を組み合わせて、正確で最新の応答を返す。

## 4. 主な利点(ページ)
- リアルタイム情報: 訓練中に利用できなかった最新データにアクセスできる。
- 外部システム統合: データベース、API、その他のサービスに接続できる。
- 動的な応答: 最新の利用可能な情報に基づいて回答できる。
- 構造化されたインタラクション: Claude は、必要な情報と、その要求方法を、正確に把握している。

ツール使用は、Claude を静的な知識ベースから、ライブデータを扱える動的なアシスタントへと変える。天気、株価、データベースクエリなど、最新の情報を必要とするアプリケーションを作れるようになる。

## 質疑(学習中の確認)
範囲: このレッスン(L20)の内容。

### 質問1: 天気APIを実際に呼び出すのは誰か
出題: 「今日の東京の気温は?」に対して、ツール使用を設定した場合、天気APIを実際に呼び出すのは誰か。
- A: Claude が、直接、天気APIを呼び出す。
- B: 自分のアプリ(サーバー)のコードが、Claude の依頼を受けて、天気APIを呼び出す。
- C: Anthropic のサーバーが、自動で、天気データを取得する。
- D: ユーザーが、天気APIの結果を手で貼り付ける。
- YUTAの回答: B(理由の記載はなかった)
- 評価: 正解。
  - B が正しい理由: Claude は「この場所の天気データがほしい」という依頼を返すだけ。実際に API を呼ぶのは、自分のアプリ側のコードで、結果を Claude に送り返す(ページのステップ2〜4)。
  - A: Claude は外部システムを直接呼び出さない。出力するのは依頼の内容で、実行はアプリの役目。
  - C: Anthropic のサーバーが自動で取得するわけではない。データ取得は、自分で用意したコードが行う。なお、Anthropic 側で動く組み込みツール(Web 検索ツールなど)は、別の仕組みで、後のレッスンで扱われると思われる(未確認)。
  - D: 手で貼る必要はない。ツール使用は、そのやり取りをプログラムで自動化する仕組み。

## 【補足】ページ外の内容(私の整理)
- 要点は**担当の分け方**。Claude 自身は外部を呼ばず、依頼を出すだけ。外部を呼ぶのは自分のアプリ側のコード。設計書で言えば、画面(Claude)が業務ロジック(アプリ)に処理を依頼し、結果を受けて表示する分担に近い。
- この分担から、設計上の責任も決まる。取得に失敗したときの処理、タイムアウト、API の認証情報の管理は、アプリ側の責任(私の整理)。
- ステップ4の「データを送り返す」には、API のメッセージ形式の決まりがある。後続のレッスン(メッセージブロックの処理、ツール結果の送信)で扱われると思われる(未確認)。ページには、コードも `stop_reason` の説明もない。
- 試験ガイドとの関係(ガイドの全文を確認): `stop_reason` が `"tool_use"` なら処理を続け、`"end_turn"` なら終了する、というエージェントループの制御(Task Statement 1.1 の付近)や、ツール使用と JSON スキーマによる構造化出力(Task Statement 4.3 の付近)など、複数の箇所に出てくる。ここから先のレッスンは、ガイドと関係が深いと見ている(重要度は、配点で確認する)。
