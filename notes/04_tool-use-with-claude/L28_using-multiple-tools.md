## 1. このレッスンの目的
会話ループとツール処理の基盤ができていれば、ツールの追加は、決まったパターンで簡単にできることを理解する。

## 2. 追加するツール(ページ)
リマインダーシステムに必要な3機能。
| ツール | 役割(ページの理由) |
|---|---|
| `get_current_datetime` | 現在の日時を取得する。Claude は現在の日時を知る必要がある |
| `add_duration_to_datetime` | 日時に期間を加算する。Claude は日時の加算が完璧ではない |
| `set_reminder` | リマインダーを設定する。設定する方法が必要 |
- `add_duration_to_datetime` と `set_reminder` は、対応するスキーマとともに提供される(ページ本文)。

## 3. 会話にツールを追加する(ページ)
`run_conversation` の `chat` 呼び出しで、新しいスキーマをツールリストに含める。
```python
response = chat(messages, tools=[
    get_current_datetime_schema,
    add_duration_to_datetime_schema,
    set_reminder_schema
])
```
- 会話中に Claude が使える3つのツールすべてを、Claude に伝える。

## 4. ツールルーターの更新(ページ)
新しいツールごとに `elif` を追加する。
```python
def run_tool(tool_name, tool_input):
    if tool_name == "get_current_datetime":
        return get_current_datetime(**tool_input)
    elif tool_name == "add_duration_to_datetime":
        return add_duration_to_datetime(**tool_input)
    elif tool_name == "set_reminder":
        return set_reminder(**tool_input)
```
- パターン: ツール名を確認し、提供された入力で対応する関数を呼び、結果を返す。

## 5. 複数ツールのテスト(ページ)
- 依頼: 「医者の予約のリマインダーを設定してください。2050年1月1日から177日後です。」
- Claude は、①日付を計算する(`add_duration_to_datetime`)、②リマインダーを設定する(`set_reminder`)、の順に行う。
- Claude は、まず何をするかを説明し、その後、適切なツール呼び出しを順番に行う。ページの会話では、目標日を2050年6月27日と計算し、その日付でリマインダーを設定している。

## 6. メッセージフロー(ページ)
会話履歴は、次の順に積み上がる。
1. リクエストを含むユーザーメッセージ
2. テキストとツール使用ブロックの両方を含むアシスタントメッセージ
3. ツール結果メッセージ
4. フォローアップのアシスタントメッセージ
- Claude は、単一のメッセージに複数のブロック(説明テキスト+ツール使用リクエスト)を含められる。

## 7. ツールを追加するパターン(ページ)
1. ツール関数の実装を作る。
2. ツールスキーマを定義する。
3. `run_conversation` のツールリストにスキーマを追加する。
4. `run_tool` にツールのケースを追加する。
- モジュール式なので、既存のコードを再構築せずに機能を拡張できる。

## 質疑(学習中の確認)
範囲: このレッスン(L28)の内容。

### 質問1: 4つ目のツール `get_weather` を追加するときの最小の変更はどれか
- A: `run_conversation` のループ本体を書き直し、天気専用の分岐を足す。
- B: `get_weather` 関数とスキーマを作り、ツールリストにスキーマを足し、`run_tool` に分岐を足す。
- C: スキーマだけ作ればよい。Claude が関数を自動で実行する。
- D: `run_tool` に分岐を足せばよい。スキーマをリストに入れなくても、Claude は関数名を知っている。
- YUTAの回答: B(「ツール基盤は作成済みであるため、関数とスキーマの作成、ツールリストの登録のみでよい」)
- 評価: 正解。理由も、ページの趣旨(基盤は変えず、ツール側を足す)に合っている。ただし、回答の理由では「`run_tool` への分岐の追加」が抜けていた。ページの4手順では、4つ目にあたる。
  - B が正しい理由: ページの4手順(関数、スキーマ、リストへの追加、`run_tool` への分岐)に一致する。
  - A: ループ本体は、`stop_reason` で判定し、実行先は `run_tool` に任せるので、ツールの数に依存しない。書き直す必要がなく、触るとリスクが増える。
  - C: Claude は関数を実行しない。Claude が出すのは ToolUse ブロック(依頼)だけで、実行はアプリ側(`run_tool`)の仕事(L24〜L25)。
  - D: Claude がツールを知る手段は、リクエストに渡した `tools` のスキーマだけ。リストに入れないツールは、Claude からは存在しないのと同じで、呼ばれない。
- 補足: `run_tool` の分岐を入れ忘れると、Claude がそのツールを呼んでも、アプリ側が実行先を知らずに失敗する。

## 【補足】ページ外の内容(私の整理)
- **未登録のツール名への備え**: ページの `run_tool` には `else` がない。ツール名が一致しないと、何も返さず `None` になる。`else: raise ValueError(f"Unknown tool: {tool_name}")` を置けば、L27 の `try/except` で拾われ、`is_error: True` で Claude に返せる(私の提案。ページには書かれていない)。
- **`elif` が増えたとき**: ツール名から関数を引く辞書で置き換える書き方もある。ページには出てこない。
- **未確認の点**: 1つの応答に複数の ToolUse が入るとき、複数の `tool_result` を1つのユーザーメッセージにまとめる規則は、このページでも扱われていない(L25 から引き続き未確認。並列ツール使用の公式ドキュメントで確認する)。
- **ページのテスト例の意味**: 「177日後」のような日付計算は、Claude 単独では誤りやすい(ページの理由)。計算をツールに任せる設計は、「得意でない処理を、確実な関数に任せる」という、ツール使用の典型的な使い方。
- **設計書で言えば**: 呼び出し表(`run_tool`)に行を足し、機能一覧(ツールリスト)に項目を足す。中心の処理を変えない拡張。
