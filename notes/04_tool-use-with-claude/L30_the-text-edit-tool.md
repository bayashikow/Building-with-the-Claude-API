## 1. このレッスンの目的
Claude に組み込まれているテキスト編集ツールで、できることと、**実装は自分で書く**という役割分担を理解する。

## 2. テキスト編集ツールとは(ページ)
- Claude には、ゼロから作る必要のない、組み込みツールが1つある。それがテキスト編集ツール。標準的なテキストエディタと同じように、ファイルやディレクトリを操作する能力を、Claude に与える。
- できること(ページの記載):
  - ファイルまたはディレクトリの内容を表示する
  - ファイル内の特定の行範囲を表示する
  - ファイル内のテキストを置換する
  - 新しいファイルを作成する
  - ファイルの特定の行に、テキストを挿入する
  - ファイルへの最近の編集を、取り消す
- ページは、これにより、Claude が最初から、ソフトウェアエンジニアとして機能する力を持つ、と説明している。

## 3. 実装の要件(ページ)
- 混乱しやすい点: ツールの**スキーマは Claude に組み込まれている**が、**実際の実装は自分で提供する**。
- Claude は、ファイル操作をどう要求するかを知っている。その操作を実際に実行するコード(ファイルの作成、ディレクトリの読み取り、テキストの置換など)は、自分で書く。
- 他のツールは、JSON スキーマと関数の実装の両方を自分で書く(L22・L23)。テキスト編集ツールは、スキーマの知識を Claude が持つ。

## 4. スキーマのバージョン(ページ)
- メインのスキーマは Claude に組み込まれているが、リクエストでは、**小さなスキーマスタブ**を含める必要がある。正確な形は、使用するモデルによって異なる。
  ```python
  def get_text_edit_schema(model):
      if model.startswith("claude-3-7-sonnet"):
          return {"type": "text_editor_20250124", "name": "str_replace_editor"}
      elif model.startswith("claude-3-5-sonnet"):
          return {"type": "text_editor_20241022", "name": "str_replace_editor"}
  ```
- Claude は、この小さなスキーマを認識し、裏側で、自動的に完全なテキスト編集ツールの仕様に展開する。

## 5. 実践例(ページ)
- 「`./main.py` を開いて、その内容を要約してください」→ ①ツールでファイルを表示する → ②内容を読む → ③要約する。
- 「`./main.py` を開いて、円周率を小数第5桁まで計算する関数を書いてください。その後、実装を試す `./test.py` を作成してください」→ ①既存の `main.py` を表示する → ②円周率計算の関数を含む新しい実装で、内容を置き換える → ③単体テストを含む新しい `test.py` を作成する。

## 6. なぜ使うのか(ページ)
最新のコードエディタに AI アシスタントが入っていても、このツールが価値を持つ場面:
- ファイルをプログラムから編集する必要があるアプリケーションを構築している。
- フル機能のコードエディタにアクセスできない環境で作業している。
- ファイル編集の機能を、Claude を活用したアプリケーションに、直接統合したい。
- 本質: 高機能な AI 搭載コードエディタの機能の多くを、自分のアプリ内で再現でき、Claude がファイルシステムとどう相互作用するかを、細かく制御できる。

## 質疑(学習中の確認)
範囲: このレッスン(L30)の内容。

### 質問1: `str_replace` の依頼が届いたとき、アプリ側の処理として適切なものはどれか
- A: Claude が実行を済ませているので、アプリは何もせず、次の依頼を待つ。
- B: 依頼のパスと、置換の対象が1か所だけ一致することを確かめてから、自分のコードで置換し、結果(または失敗の内容)を `tool_result` で返す。
- C: スキーマが組み込みなので、`tool_result` は返さなくてよい。
- D: 依頼のパスを検証せず、そのままファイルを書き換える。Claude の依頼は、常に安全だから。
- YUTAの回答: B(「Claude はツールの実行が成功したのか失敗したのか分からないため、結果を返す必要がある」)
- 評価: 正解。理由も、ツール使用の基本(L25・L27)を押さえている。補足すると、`tool_use` に対する `tool_result` が欠けると、次のリクエストが API のルール違反でエラーになる(L25 で確認した公式ドキュメントの記述)。失敗した場合は、`is_error: True` と、原因が分かる内容を返す(L27)。
  - A: テキスト編集ツールも、実行するのはアプリ側(クライアント側のツール)。Claude は、ファイルに触れない。何もしないと、ファイルは変わらず、結果も返らず、会話が止まる。
  - C: スキーマが組み込みなのは、依頼の書式だけの話。`tool_result` を返す決まりは、他のツールと同じ。
  - D: ファイルシステムに触れるので、パスの検証などの安全対策が必要。Claude の依頼が常に安全とは、前提にできない。
- 補足: B の「置換の対象が1か所だけ一致することを確かめる」は、公式ドキュメントの安全対策の1つ。0か所だと何も変わらず、2か所以上だと意図しない箇所を壊すため。設計書で言えば、依頼を受ける側が、受け付け前の入力チェックの責任を持つ構図。

### ex13 の題材の解説(2026-11-14。演習は実施せず、解説のみ)
題材: 私が書いた `TextEditorTool` と、ツールの登録・振り分けのコード(教材のコードそのものではない)。私の環境で実験を実行し、結果を確かめた。

| # | 箇所 | 何が起きるか | 直し方(方針) |
|---|---|---|---|
| 1 | `_validate_path` の `startswith(self.base_dir)` | 許可フォルダが `.../app` のとき、名前が似た `.../app_old/...` も通る | フォルダの境界まで見る |
| 2 | スキーマの `name` と、`run_tool` の比較文字列が違う | 依頼が、毎回 `Unknown tool name` のエラーになる | 名前を、1か所だけで定義する |
| 3 | `insert` が未実装(題材で簡略化のため省いた)。`undo_edit` は実装済み | `insert` の依頼で、エラーになる。`undo_edit` は、新しい版で削除されており、使われない処理が残る | 使うバージョンの仕様と、実装を突き合わせる |
| 4 | バックアップが `名前.bak` の1つだけ | 同じファイル名が別フォルダにあると、上書きされる。取り消しも1段だけ | パスごとに別名にする |

**#1 パスの検証**
- 実験の結果: `../../etc/passwd` は拒否されたが、`../app_old/secret.txt` は**通って**、中身が見えた。
- 理由: `normpath` が `..` を解決すると、`.../app_old/secret.txt` になる。これを `.../app` で前方一致すると、`app` の後に `_old` が続くだけなので、**文字列としては一致**する。見たいのは、フォルダとしての内側かどうか。
- 直し方: `abs_path == base` か、`abs_path.startswith(base + os.sep)` で確かめる。または `os.path.commonpath` を使う。シンボリックリンクで外に出る場合に備えて、`realpath` を使う方法もある(私の整理。公式ドキュメントには、ディレクトリトラバーサルの防止、としか書かれていない)。
- 実運用での事故の例: Claude は、利用者の依頼や、読み込んだファイルの内容に影響される。外部の内容に紛れた指示で、別フォルダの設定ファイル(認証情報など)を読み出したり、上書きしたりする。L25 の、ツール結果の内容は信頼しない、という警告と同じ方向の話。

**#2 名前の不一致**
- 実験の結果: `is_error: True`、内容は `Error: Unknown tool name: str_replace_based_edit_tool`。
- 理由: スキーマ側(新しい名前 `str_replace_based_edit_tool`)と、振り分け側(古い名前 `str_replace_editor`)が、別々に書かれている。どちらの部品も、単体では正しく動く。つなぐ部分だけが合っていない。結合テストでしか見つからない、典型的な不具合。
- 実運用での事故の例: ツールが、一度も動かないのに、アプリ全体は、エラーを返しながら動き続ける。Claude は、失敗を受けて再試行したり、利用者に謝ったりするだけで、原因に気づけない(L27 の `is_error` の動き)。
- 直し方: 名前は、定数1か所で定義し、スキーマも振り分けも、そこを参照する。現在の指定は、`type` が `text_editor_20250728`、`name` が `str_replace_based_edit_tool`。

**#3 コマンドの網羅**
- 公式ドキュメントに載っているコマンドは、`view`・`str_replace`・`create`・`insert`。題材は `insert` を実装していないので、`insert` の依頼が来ると、`Unknown text editor command: insert` になる。
- `undo_edit` は、公式ドキュメントでは、新しい版で削除されている。題材は、これを実装しているので、使われない処理が残っている状態。
- 直し方: 使うバージョンの仕様(ドキュメント)を基準に、コマンドの一覧と、実装を突き合わせる。

**#4 バックアップ**
- `os.path.basename` だけで名前を付けているので、`a/note.txt` と `b/note.txt` が、同じバックアップ `note.txt.bak` を共有する。`str_replace` のたびに、上書きもされる。

**問題ではない部分(実験3)**
- `hello` が2か所のとき、「2か所に一致した。一意になるよう、文脈を足して」というエラーになり、0か所のときは「一致なし」になる。どちらも、Claude が次に何をすればよいか、判断できる内容。ドキュメントの「ちょうど1か所に一致させる」と同じ方針で、良い例。

**まとめ(原則)**
- ツールの依頼を実行するのは、アプリ側。検証(パス、一致数)の責任も、アプリ側が持つ。
- 結果は `tool_result` で返し、失敗は `is_error` で伝える(L25・L27)。
- 部品が単体で正しくても、つなぎ(名前、コマンドの一覧)が合っていないと動かない。
