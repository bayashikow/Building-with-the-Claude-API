## 1. このレッスンの目的
ツールを使えるようにする API 呼び出し(`tools` パラメータ)と、ツール使用時に返る、複数のブロックを含む応答(マルチブロックメッセージ)の扱い方を理解する。

## 2. ツール対応の API 呼び出し(ページ)
Claude がツールを使えるようにするには、API 呼び出しに `tools` パラメータを含める。
```python
messages = []
messages.append({
    "role": "user",
    "content": "What is the exact time, formatted as HH:MM:SS?"
})

response = client.messages.create(
    model=model,
    max_tokens=1000,
    messages=messages,
    tools=[get_current_datetime_schema],
)
```
- `tools` は、Claude が呼び出せる関数を記述する JSON スキーマ(L23)のリストを受け取る。

## 3. マルチブロックメッセージ(ページ)
- これまでの単一のテキストブロックの応答とは異なり、Claude がツールを使うと決めたとき、アシスタントメッセージの `content` リストに**複数のブロック**が入る。
- 通常、次の2種類が含まれる。
  | ブロック | 内容 |
  |---|---|
  | テキストブロック | Claude が何をしているかを説明する、人が読めるテキスト(例:「現在の時刻を調べるお手伝いができます。その情報を調べてみます」) |
  | ToolUse ブロック | どのツールを呼び、どのパラメータを使うかについての、あなたのコードへの指示 |
- ToolUse ブロックの中身:
  1. ツール呼び出しを追跡するための **ID**
  2. 呼び出す関数の**名前**(「get_current_datetime」など)
  3. 辞書形式の**入力パラメータ**
  4. **タイプ**指定: `"tool_use"`

## 4. 会話履歴の管理(ページ)
- Claude は会話履歴を保存しない。履歴は手動で管理する。
- ツールの応答を扱うときは、**すべてのブロックを含む、コンテンツ構造全体**を保持する。
  ```python
  messages.append({
      "role": "assistant",
      "content": response.content
  })
  ```
- これでテキストブロックと ToolUse ブロックの両方が保たれる。後続の API 呼び出しで、会話のコンテキストを維持するために非常に重要。

## 5. ツール使用の完全なフロー(ページ)
1. ツールスキーマを含むユーザーメッセージを Claude に送信する。
2. テキストブロックと ToolUse ブロックを含むアシスタントメッセージを受信する。
3. ツール情報を抽出し、実際の関数を実行する。
4. 完全な会話履歴とともに、ツールの結果を Claude に送り返す。
5. Claude から最終的な応答を受信する。

- 各ステップで、Claude が正確な応答を出すのに必要な完全なコンテキストを持てるよう、メッセージ構造を注意深く処理する。

## 6. ヘルパー関数の更新(ページ)
- `add_user_message()`、`add_assistant_message()` のようなヘルパーは、マルチブロックのコンテンツを扱えるよう更新が必要。
- 現在のバージョンは、おそらく単一のテキストブロックしか想定していない。今後は、ToolUse ブロックを含む、より複雑なコンテンツ構造に対応する。

## 質疑(学習中の確認)
範囲: このレッスン(L24)の内容。

### 質問1: テキストと ToolUse を含む応答を、履歴にどう追加するか
出題: Claude がテキストブロックと ToolUse ブロックを含む応答を返した。会話履歴への追加として、最も適切なものは。
- A: テキストブロックの文字列だけを、`{"role": "assistant", "content": text}` として追加する。
- B: `{"role": "assistant", "content": response.content}` として、すべてのブロックを追加する。
- C: ToolUse ブロックの `name` と入力だけを抜き出して、文字列にして追加する。
- D: 何も追加せず、ツールの結果だけを次のメッセージに入れる。
- YUTAの回答: B(理由の記載はなかった)
- 評価: 正解。
  - B が正しい理由: ページの趣旨は「すべてのブロックを含む、コンテンツ構造全体を保持する」。`response.content` をそのまま追加すれば、テキストと ToolUse の両方が元の形で残り、次の呼び出しで Claude は「どのツールを、どの ID で呼んだか」を確認できる。
  - A: ToolUse ブロックが失われる。後で返すツールの結果と、元の呼び出しとの対応(ID)が取れなくなる。API 側でも、ツールの結果に対応する呼び出しがないとエラーになる可能性がある(私の理解で、未確認)。
  - C: 文字列にすると、ブロックの構造(タイプ、ID)が失われ、Claude が自分の呼び出しとして認識できる形ではなくなる。
  - D: 履歴に Claude の応答がないまま結果だけを送ると、会話が成り立たない。Claude は履歴を保存しないので、自分で保持して渡す必要がある(ページの記述)。
- 補足: `response.content` をそのまま渡すのは、簡単に見えて設計上の意味が大きい。取り出した一部を自分で組み直すと、ID などの欠落が起きやすい。結合テストで、部品間の受け渡しを加工せずに渡す理由と同じ(私の整理)。
