## 1. このレッスンの目的
ツール使用とストリーミングを組み合わせたときの、引数の届き方(バッファリングと検証)と、それを無効にする「細粒度のツール呼び出し」の使いどころと注意点を理解する。

## 2. 基本のツールストリーミング(ページ)
- ストリーミングを有効にすると、Claude は処理中に、種類の異なるイベントを返す。テキスト生成の `ContentBlockDelta` に加えて、ツール使用では、`InputJsonEvent`(コード上は `chunk.type == "input_json"`)も処理する必要がある。
- 各イベントの重要なプロパティ:
  | プロパティ | 内容 |
  |---|---|
  | `partial_json` | ツール引数の一部を表す JSON のチャンク |
  | `snapshot` | これまでに受信したすべてのチャンクから作られた、累積の JSON |
  ```python
  for chunk in stream:
      if chunk.type == "input_json":
          print(chunk.partial_json)       # 部分的なチャンク
          current_args = chunk.snapshot   # これまでの完全なスナップショット
  ```

## 3. JSON 検証の仕組み(ページ)
- Anthropic API は、Claude が生成したチャンクを、すぐには送らない。**チャンクをバッファリングして、先に検証する**。
- API は、何かを送る前に、**完全なトップレベルのキーと値のペア**を待つ。ページの例:
  ```json
  {
    "abstract": "This paper presents a novel...",
    "meta": {
      "word_count": 847,
      "review": "This paper introduces QuanNet..."
    }
  }
  ```
  1. `abstract` の値全体が完成するまで待つ。
  2. そのキーと値のペアを、スキーマに対して検証する。
  3. `abstract` のためにバッファリングしたチャンクを、一度に送る。
  4. `meta` オブジェクトについて、同じことを繰り返す。
- この仕組みのため、ストリーミングが有効でも、テキストが**遅延の後にまとめて表示される**。

## 4. 細粒度のツール呼び出し(ページ)
- より速く、細かいストリーミングが必要なとき(利用者への即時の更新、部分的な結果の処理の早期開始など)に有効にする。
- 主な働きは1つ: **API 側の JSON 検証を無効にする**。その結果:
  - Claude が生成するとすぐに、チャンクを取得できる。
  - トップレベルのキーの間での、バッファリングの遅延がない。
  - より従来型のストリーミング動作になる。
- **重要: JSON 検証が無効なので、コードは無効な JSON を処理する必要がある。**
- ページの有効化の例(コース側の自作ヘルパー):
  ```python
  run_conversation(messages, tools=[save_article_schema], fine_grained=True)
  ```
- `meta` オブジェクト全体の完成を待たずに、ストリームのかなり早い段階で `word_count` の値を受け取れる場合がある。

## 5. 無効な JSON の処理(ページ)
- 細粒度では、`"word_count": undefined` のような、数値の代わりに無効な JSON を、Claude が生成する可能性がある。
  ```python
  try:
      parsed_args = json.loads(chunk.snapshot)
  except json.JSONDecodeError:
      print("Received invalid JSON, continuing...")
  ```
- 細粒度を使わない場合、API の検証がこのエラーを捕捉し、問題のある値を文字列で包むことがある。ただし、期待するスキーマと合わない場合がある。

## 6. 使うべき場面(ページ)
次の場合に、細粒度を検討する。
- ツール引数の生成について、利用者にリアルタイムの進行状況を見せたい。
- 部分的なツール結果の処理を、できるだけ早く始めたい。
- バッファリングの遅延が、利用者体験に悪影響を与えている。
- 堅牢な JSON エラー処理を実装することに、抵抗がない。

ほとんどのアプリケーションでは、検証ありのデフォルトの動作で十分。

## 質疑(学習中の確認)
範囲: このレッスン(L29)の内容。

### 質問1: 細粒度を有効にしたとき、アプリ側の追加対応が必要な理由はどれか
- A: API が引数の JSON を検証しなくなるので、受け取った JSON が壊れている可能性があるから。
- B: ツールの関数が、実行されなくなるから。
- C: `tool_result` を、返す必要がなくなるから。
- D: 引数が、すべて1つのチャンクにまとめて届くようになるから。
- YUTAの回答: A(「通常は、トップレベルのキーと値のペアが1組そろうまでチャンクをためて、スキーマで検証を行うが、細粒度のツール呼び出しの場合、検証せずに生成された順に送るから」)
- 評価: 正解。理由も、ページの内容を押さえている。
  - A が正しい理由: 細粒度は、API 側の検証を無効にする。検証済みという保証がなくなるため、受け取った側で、壊れた JSON を処理する必要がある。
  - B: 関数を実行するのは、これまで通りアプリ側。細粒度は、引数の**届け方**の話で、実行の仕組みは変わらない。
  - C: `tool_result` を返す必要は、変わらない(L25)。
  - D: 逆。標準の動作のほうが、検証を済ませた塊で、まとめて届く。細粒度のほうが、生成された順に、細かく早く届く。
- 補足: YUTAから「細かいことを理解できていないかもしれない」と相談があり、次の点を補足した(私の整理)。
  1. API が検証しているのは、キーに対する値の「型や形」がスキーマに合うか(例: `word_count` が数値か)。この検証の時間が、チャンクを溜める理由。
  2. 溜める単位が「トップレベルの1組」なので、1つの値が長いとき(例: `abstract`)、その値が書き終わるまで、何も届かない。細粒度が効くのは、こうした長い値のとき。
  3. 途中の `snapshot` は、未完成で当たり前(例: `{"abstract": "This pap` は、閉じ括弧がなく、`json.loads` が必ず失敗する)。ページの `try/except` で `continue` するのは、これを受け流すため。
  4. 本当に困る失敗は、ブロックが完成した後も不正な場合(例: `"word_count": undefined`)。見分けるのは、ブロックの完了時。

### 質問2: 「トップレベルの1組」とは何か
- YUTAの質問: 「トップレベルの1組とは何ですか？」
- 回答の要点: 引数の JSON の、一番外側の `{ }` の直下にある「キー: 値」の1組。ページの例では、`abstract: "..."` が1組目、`meta: { ... }` が2組目。`meta` の中の `word_count` や `review` は、1段内側なので、`meta` という1組の**中身**として扱われる。標準の動作では、`meta` の `{ }` が閉じるまで溜め、検証してから送る。
- 設計書で言えば、一番外側の項目を、大項目として1つずつ検収するイメージ。大項目の中の小項目は、1つ終わるごとには検収されない。

### 質問3: 有効にすると、ツールの結果の返答が、細切れに届くのか
- YUTAの質問: 「ツールの定義に足すとのことですが、ツールに足して、その結果に対する返答を細切れに受け取れる、ということですか？」
- 回答の要点: **違う**。細切れになるのは、ツールの結果ではなく、**Claude が出す、ツール呼び出しの依頼(引数)**。
  - 流れ: ①アプリが、ツール定義(`eager_input_streaming: True` 付き)とともに、リクエストを送る → ②Claude が、ツールの引数を書き始める。この引数が、細切れ(`partial_json`)で、アプリに届く(Claude → アプリの向き) → ③`content_block_stop` で、引数が完成する → ④アプリが、完成した引数で関数を実行する → ⑤`tool_result` を、Claude に返す(アプリ → Claude の向き)。⑤は、これまでと変わらない。
  - ツール定義のフィールドは、「このツールの引数を、検証を待たずに、早く流してください」という、API への指示。
  - 例えば、長い文章を引数に持つツール(ファイルへの書き込みなど)で、引数の生成の進み具合を、利用者に見せられる。
- 追加の質問(YUTA): 「引数を細切れに受け取ったところで、ツール実行はできないと思うが」→ そのとおり。ツールの実行は、引数が完成し(`content_block_stop`)、`json.loads` で解釈できた後に、これまでと同じく `run_tool` で行う。細切れで受け取る目的は、実行を早めることではなく、**引数の生成の途中で、アプリ側が別の処理をできること**(進行状況の表示、部分的な結果の処理の早期開始)。
  - 私の整理: 検証されていない途中の値は、壊れていても困らない処理(画面表示など)に使うのが安全。実行や保存など、取り消しにくい処理は、完成して解釈できてから行う。標準のバッファリングでも、完成後に実行する点は同じで、違いは、完成までの間に何が見えるか。

## 【補足】ページ外の内容(私の整理)
### 公式ドキュメントでの確認(確認日 2026-11-14)
出典: [Fine-grained tool streaming](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)(Claude Platform Docs。ページを取得して確認した。以下は私による要約)。

**有効にする方法**
- 公式の名前は「fine-grained tool streaming」。サーバー側のバッファリングと JSON 検証をせずに、Claude が生成するのと同時に、ツールの入力を配信する。
- **各ユーザー定義ツールの定義に `"eager_input_streaming": True` を足す**(`name`、`description`、`input_schema` と同じ階層)。そのうえで、リクエストをストリーミングで送る。
  ```python
  tools=[{
      "name": "make_file",
      "description": "Write text to a file",
      "eager_input_streaming": True,
      "input_schema": {...},
  }]
  ```
- このフィールドは任意。`true` で、そのツールが細粒度になる。省略すると、標準のバッファリング。
- ページの `fine_grained=True` は、コースの自作ヘルパーの引数で、API の名前ではない。
- 以前の方法のベータヘッダー `fine-grained-tool-streaming-2025-05-14` は、フィールドを設定しないツールを、細粒度にする。ツールごとのフィールドが、このヘッダーの代わりになり、明示的な `false` は、ヘッダーを送っても、そのツールをバッファリングのままにする。ヘッダーは、computer use や browser use のツールセットの項目とは併用できない。

**届くイベントの順序**(`tool_use` のブロック)
1. `content_block_start`: `content_block.type == "tool_use"`。`input` は `{}` の仮の値。
2. `content_block_delta`(繰り返し): `delta.type == "input_json_delta"`。`delta.partial_json` に、入力の文字列の断片が入る。
3. `content_block_stop`: ブロックが完成。
- `partial_json` は、解釈済みの値ではなく、文字列の断片。最初の `input: {}`(オブジェクト)と、`partial_json`(文字列)の型の違いは、設計どおり。
- 標準のバッファリングと比べて、断片は、Claude がパラメータを書き始めた瞬間から届き、通常は長めで、単語の途中での切れ目が少ない。
- コースの `input_json` イベント(`partial_json` と `snapshot`)は、より高位の SDK のイベント。ドキュメントの最初の例も、この高位のイベントを使っている。生の SDK のイベントは、上の `content_block_*`。

**ためて、解釈する手順**(ドキュメントの流れ)
1. `tool_use` の `content_block_start` で、`input_json = ""` にする。
2. 各 `input_json_delta` で、`input_json += event.delta.partial_json` と足す。
3. `content_block_stop` で、ためた文字列を解釈する(`json.loads` を `try/except` で保護する)。
- 解釈は、`content_block_stop` の時点だけにする。コースのページは、`snapshot` を届くたびに `json.loads` する書き方で、途中の未完成な JSON は、失敗して当たり前。ドキュメントの「完成時に1回、解釈する」ほうが素直(質疑の補足 3・4 と同じ点)。
- 応答が `max_tokens` で止まった場合、パラメータが途中で切れることがある。`max_tokens` を増やして再試行するか、部分的な入力を修復するかを、決める。

**無効な JSON のとき**
- 入力が無効または不完全なら、ツールは実行できない。失敗を、`tool_result` として Claude に返す。
- 解釈できなかった入力を、1つのキー(`INVALID_JSON`)で包み、文字列にして、`is_error: true` の `tool_result` の `content` に入れる。
  ```python
  def invalid_input_result(tool_use_id, raw_input):
      return {
          "type": "tool_result",
          "tool_use_id": tool_use_id,
          "is_error": True,
          "content": json.dumps({"INVALID_JSON": raw_input}),
      }
  ```
  (ドキュメントに、この手順のコードは無く、ガイダンスに沿った例として示されている。)
- 包みは、文字列の連結ではなく、JSON ライブラリで作る。引用符などの特殊文字が、正しくエスケープされるため。
- L27 の `is_error` と同じ考え方。

**その他**
- 全モデル・主要プラットフォームで使える、と書かれている(検索結果の抜粋に基づく)。

### 設計上の読み取り
- 標準は「受入検査を通ってから渡される」、細粒度は「検査前の半製品が先に流れてくる」。早く使える代わりに、受け取る側が検査の責任を持つ。
- 判断の軸: **体験(最初の反応までの速さ)と、確実性(検証済みであること)の、引き換え**。ほとんどのアプリケーションでは、標準で足りる(ページ)。
- L07(ストリーミング)の続き。通常のテキストの `ContentBlockDelta` に加え、ツール引数の `input_json` を扱う。
- 試験ガイドとの関係: ツールの引数の検証や、不正な入力への対処は、ガイドの Task Statement 4.3(`tool_use` と JSON スキーマ)の付近に関係しうる。ストリーミングの細粒度の指定が出題されるかは、確認していない(出題の内容は予想しない)。
