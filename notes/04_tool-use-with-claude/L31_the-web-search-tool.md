## 1. このレッスンの目的
Claude に組み込まれた Web 検索ツールの設定、レスポンスに含まれるブロック、検索ドメインの制限、結果の表示方法を理解する。

## 2. 前提(ページ)
- **使う前に、組織が、設定コンソールで、Web検索ツールを有効にする必要がある**(設定の確認先: https://platform.claude.com/settings/privacy)。
- Claude には、ユーザーの質問に答えるために、最新または専門的な情報を、インターネットで検索できる、組み込みの Web 検索ツールがある。
- 実装を提供する必要がある他のツール(L22〜L28)とは異なり、Claude は、**検索のプロセス全体を自動的に処理する**。有効にするための、シンプルなスキーマを提供するだけでよい。

## 3. 設定(ページ)
```python
web_search_schema = {
    "type": "web_search_20250305",
    "name": "web_search",
    "max_uses": 5
}
```
- `max_uses`: Claude が実行できる**検索の回数を制限**する。Claude は、初期結果に基づいて、追加の検索をすることがある。過剰な API 呼び出しを防ぐ。1回の検索で複数の結果が返るが、Claude が、追加の検索が必要と判断することもある。
- API 呼び出しの `tools` 配列に、スキーマを含めるだけでよい。Claude が、ユーザーの質問に答えるために、Web 検索が役立つかどうかを、自動的に判断する。

## 4. レスポンスの仕組み(ページ)
Web 検索ツールを使うと、レスポンスに、複数の種類のブロックが含まれる。
| ブロック | 内容 |
|---|---|
| テキストブロック | Claude が何をしているかの説明 |
| `ServerToolUseBlock` | Claude が使った、正確な検索クエリ |
| `WebSearchToolResultBlock` | 検索結果を含む |
| `WebSearchResultBlock` | タイトルと URL を持つ、個々の検索結果 |
| 引用ブロック | Claude の発言を裏付けるテキスト |
- この構造で、Claude が何を検索し、どのソースを見つけたかを、正確に確認できる。
- 引用には、Claude が回答を裏付けるために使った、特定のテキストと、ソースの URL が含まれる。

## 5. 検索ドメインの制限(ページ)
`allowed_domains` で、検索を特定のドメインに限定できる。信頼性の高い、権威あるソースを求める場合に便利。
```python
web_search_schema = {
    "type": "web_search_20250305",
    "name": "web_search",
    "max_uses": 5,
    "allowed_domains": ["nih.gov"]
}
```
- 例: 医療やエクササイズのアドバイスなら、PubMed(nih.gov)のようなドメインに限定すると、ランダムなブログではなく、根拠に基づいた情報が得られる。

## 6. 検索結果のレンダリング(ページ)
- テキストブロックは、通常のコンテンツとして、レンダリングする。
- Web 検索結果は、上部に、ソースのリストとして表示する。
- 引用は、テキストの中に、インラインで表示し、ソースのドメイン、ページタイトル、URL、引用したテキストを含める。
- 利用者が、Claude が回答に到達した過程を理解でき、使われているソースの透明性につながる。どの情報が、どのソースから来たかが明確になり、AI の回答への信頼を築く。

## 7. 実践的な使い方(ページ)
最も効果的な場面:
- 最新の出来事や、最近の動向
- Claude の訓練データにない、専門的な情報
- ファクトチェックと、権威あるソースの発見
- 最新情報を必要とする、研究タスク

## 質疑(学習中の確認)
範囲: このレッスン(L31)の内容。

### 質問1: Web検索ツールを使うとき、アプリ側が行うことはどれか
- A: 検索を実行する関数を自分で書き、結果を `tool_result` で、Claude に返す。
- B: `type` と `name` などを持つスキーマを `tools` に渡す。検索は Anthropic 側が実行し、結果と引用は、レスポンスに含まれて返る。
- C: 検索結果を受け取るたびに、アプリ側のツール実行のループで、結果を返し直す。
- D: スキーマは要らない。プロンプトに「ウェブで検索して」と書けば、使える。
- YUTAの回答: B(「検索自体は Anthropic のサーバーで行われるため」)
- 評価: 正解。理由も、ページの趣旨(検索のプロセス全体を、Claude 側が自動で処理する)を押さえている。
  - A: 検索を実行する関数を自分で書くのは、L22〜L28 のツール(クライアント側のツール)の話。Web検索ツールは、検索の実行が Anthropic 側なので、関数も `tool_result` の返却も要らない。
  - C: 検索の結果は、同じレスポンスの中に、ブロックとして含まれて返る。L27 のような、アプリ側のツール実行のループで、結果を返し直す必要はない(ページの記述)。
  - D: スキーマ(`type` と `name`)を `tools` に渡さないと、ツールとして有効にならない。プロンプトに「検索して」と書くだけでは、検索は動かない。
- 補足: 検索の実行が Anthropic 側でも、アプリ側の責任は、別の形で残る。①設定する(`max_uses`、`allowed_domains`)②結果と引用を、利用者に見せる ③検索の失敗に気づく(下の【補足】のとおり、HTTP 200 のまま、本体のエラーで返る)。ページの `ServerToolUseBlock` の「Server」は、サーバー側で動く種類のツールを表す(私の整理。ページに、はっきりした説明はない)。

## 【補足】ページ外の内容(私の整理)
### 公式ドキュメントでの確認(確認日 2026-11-14)
出典: [Web search tool](https://platform.claude.com/en/docs/agents-and-tools/tool-use/web-search-tool)(Claude Platform Docs。検索結果の抜粋に基づく。ページ全体は読んでいない)。以下は私による要約。
- **版**: Web検索ツールは、3つの版がある。`web_search_20250305`(基本の検索)、`web_search_20260209`(動的フィルタリングを追加)、`web_search_20260318`(エージェント型ワークフロー向けの、レスポンスへの包含の制御を追加)。ドキュメントの例は、基本に `web_search_20250305`、動的フィルタリングに `web_search_20260318` を使っている。ページの `web_search_20250305` は、基本版として、現在も載っている。
- **動的フィルタリング**: コード実行の内部から、Web検索を実行する。`web_search_20260209` 以降では、`allowed_callers` が、既定で、コード実行経由(`code_execution_20260120`)になる。直接呼び出す場合は、`allowed_callers: ["direct"]` を指定する(プログラム的なツール呼び出しに対応しないモデルでは、これが必要。未設定だと、400 エラーで案内される、という趣旨の記述を見た)。必要な場合に、ドキュメントで確かめる。
- **`max_uses` を超えた場合**: Claude が許可された回数より多く検索しようとすると、`web_search_tool_result` が、エラーコード `max_uses_exceeded` のエラーになる。失敗した検索も、上限に数えられる。
  - 目安(ドキュメントの記述): 単一の事実の確認は、通常 1〜3 回。比較的な調査や、複数の対象の調査は、10 回以上になることがある。調査用のエージェントは、`max_uses` を 15〜20 にするか、省略する。
- **ドメイン指定**:
  - `allowed_domains` と `blocked_domains` は、どちらか一方だけ。両方を指定すると、API は 400 エラーを返す。
  - ドメインは、`https://` を付けない(例: `example.com`)。サブドメインは、自動で含まれる。サブパス(`example.com/blog`)も指定できる。
  - 組織レベルのドメイン制限(コンソール)がある場合、リクエストのドメインは、それをさらに絞ることしかできず、広げられない。組織の設定と衝突するドメインを指定すると、検証エラーになる。
- **エラーの返り方**: レート制限などのエラーでも、API は 200(成功)を返す。エラーは、レスポンス本体の `web_search_tool_result` の中の `web_search_tool_result_error` で表される。エラーコード: `too_many_requests`(レート制限)、`invalid_input`(無効な検索クエリのパラメータ)、`max_uses_exceeded`、`query_too_long`、`unavailable`(内部エラー)。L27 の `is_error` とは、違う仕組み。HTTP のステータスや `stop_reason` だけでは、検索の失敗に気づけない。
- **引用の表示**: ウェブの結果、またはそこに含まれる情報をエンドユーザーに表示する場合、インラインの引用を、UI の中で、はっきり見えて、クリックできるようにしなければならない。
- **使用量の確認**: レスポンスの `usage` に、`server_tool_use` の `web_search_requests`(検索の回数)が入る。
- **検索の頻度の調整**: 検索のトリガーは、システムプロンプトで調整できる。回数を強制的に抑えるには、`max_uses` を使う。
- **ローカライズ**: `user_location` パラメータで、利用者の位置に合わせた検索結果にできる(旧ドキュメントの記述。詳細は未確認)。
- ページ冒頭の、組織による有効化の設定は、ドキュメント側では、この抜粋では確認していない(ページの記述のまま)。

### 設計上の読み取り
- これまでのツールは、「依頼 → アプリが実行 → `tool_result`」だった。Web検索は、実行も Anthropic 側で行うので、アプリ側が結果を返さない。
- 判断の軸: **実行をサーバーに任せる便利さと、アプリ側に残る責任**(上限の設定、ソースの限定、結果と引用の表示、失敗への気づき)。
- 設計書で言えば、外部の検索サービスを呼ぶ処理を、自分で作らず、基盤側の部品として借りる。借りる分、部品の仕様(上限、エラーの形式、表示のルール)に、アプリを合わせる責任が出る。
- L29 の細粒度のツール呼び出しや、L30 のテキスト編集ツールとの違い: テキスト編集ツールは、スキーマが組み込みで、実装は自分(クライアント側のツール)。Web検索は、スキーマも実装も、サーバー側。
